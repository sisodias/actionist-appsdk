# Actionist Block Hub

Updated: 2026-08-28

The Block Hub joins business needs to reusable surfaces, capabilities, products, engines and source candidates. It does not treat every repository, page or UI component as the same kind of block.

## Six levels

1. **UI component** — hero, card, table, chart, form control or navigation element.
2. **Surface recipe** — landing page, pricing page, product detail, checkout, dashboard or portal.
3. **Capability block** — entitlement, approval, tax, fulfilment, notification or metering behavior.
4. **Product module** — CRM, support desk, CMS, project system, commerce system or LMS.
5. **Engine/platform block** — identity, data, search, payments, workflow, files, connectors or analytics.
6. **Composition recipe** — Digital Business OS, SaaS OS, Ecommerce OS, Marketing Agency OS or Course Creator OS.

The 21st.dev stores primarily supply components and visual precedents for levels 1–2. The 68-family universe and 191-source registry supply candidates for levels 3–5. Actionist owns the contracts and assembly logic that produce level 6.

## Business lifecycle

Blocks are organized by the job they perform:

`acquire → sell → activate → deliver → support → retain → operate → measure → govern`

This prevents the hub from becoming a random feature list. Every block must name an outcome, required surfaces, business-model recipes, source families and candidate implementations.

## Shared foundation and overlays

- `digital_business_os` is the horizontal foundation: identity, employees, roles, settings, navigation, audit, notifications, search, files, workflow, connectors, analytics, admin, public web, CRM, scheduling, support, projects, collaboration and payments.
- `saas` adds plans, subscriptions, entitlements, provisioning, metering, onboarding, product analytics, rollout, customer success, roadmap, incidents, API access and lifecycle marketing.
- `ecommerce` adds catalogue, storefront, cart, checkout, inventory, orders, tax, risk, fulfilment, shipping, returns, promotions, reviews and recovery.
- `marketing_agency` adds client portal, briefs, proposals, contracts, campaign calendar, assets, approvals, social publishing, reporting, capacity, retainer finance and bounded editing.
- `course_creator` adds course delivery, cohorts, progress, community, live events, assignments, certificates, memberships, referrals, sequences, learner portal and media delivery.

Employees are not an afterthought. The shared foundation includes users, teams, employee lifecycle, assignment ownership and roles/permissions because these products will usually be operated by multiple staff members.

## Candidate funnel

For each block:

1. Join existing local evidence and source candidates.
2. Discover 20–30 credible candidates when the local supply is thin.
3. Read the strongest five at product and architecture level.
4. Select one primary implementation, one backup and one pattern/reference.
5. Search again only for unresolved specialist gaps.
6. Write the seven linked module records for selected candidates.
7. Run the deterministic composer before implementation.

Use 50–100 candidates only for strategically difficult or ambiguous blocks. A hundred shallow rows for every block would recreate the Phase 7 denominator problem.

## Ranking dimensions

- outcome and product completeness;
- architecture and source quality;
- API, event and extension seams;
- reuse shape and Actionist integration fit;
- runtime and database burden;
- identity, tenancy and authority fit;
- testability and observability;
- maintainability and upstream synchronization;
- design/token adaptability;
- local/client precedent;
- licence or clean-room reimplementation cost as a trade-off, not an automatic rejection.

## Generated artifacts

- `block-register.json` — canonical block requirements, recipe membership, family joins, coverage and top candidates.
- `composition-recipes.json` — complete block membership for the shared foundation and four overlays.
- `block-source-edges.jsonl` — ranked block-to-source edges derived from the permanent source registry.

Nothing in the hub is admitted merely because it appears here. The current state is requirements mapped and source candidates joined, with qualification and implementation still separate.

## Targeted gap-search result

The first post-join GitHub pass searched only the fourteen thin or Actionist-owned blocks. It found credible new leads for employee onboarding, feature flags and webhook/API-key infrastructure. It found only primitive-level entitlement supply, weak customer-success supply, and no convincing standalone OSS products for SaaS provisioning, ecommerce tax, fraud, reviews or affiliate operations. Returns and promotions appear more likely to be sub-capabilities inside complete commerce engines such as Medusa or Saleor than standalone blocks.

These are discovery leads, not promoted sources. The thin/gap status remains until source-level product behavior and integration seams are verified.
