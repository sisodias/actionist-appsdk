**The transferable rule, stated in the source and directly applicable to P03's shelf:**

> "Owning too much code is not the failure mode. **The failure mode is owning the
> security-critical parts while renting the parts that define your product.**"

Its two tests are the reusable mechanism: (1) *Would upstream ever ship something here that
we would actually want?* Yes → stay downstream. No → take the code. (2) *Which code is a
liability to own vs a liability not to own?* Security-critical/legally-loaded → rent;
anything defining product feel → own.

The document also settles the data-layer question with a reason P03 inherits: the donors
are Postgres-shaped (Plane's Django ORM emits Postgres-specific SQL — array fields, JSONB
operators, `SELECT FOR UPDATE`; Documenso and Papermark are Prisma-on-Postgres), so
"SQLite vs Postgres" is really "do we own these codebases". Chosen: **one Postgres server,
separate schemas per donor** — one backup and one monitor, while each donor keeps its own
migration history. Honest cost, stated: cross-schema joins are gone; cross-donor questions
must be answered by consuming events into SISO-owned tables (which is why Svix + the event
envelope exist). Convex rejected (hosted proprietary). Rust rejected for this build.
