What we learned

Current synthesis from the research packet. Exact records and complete source artifacts remain visible below.

Research conclusions

  • The host owns authority: identity, tenant, URL space, navigation registry and settings provenance.
  • PackagingProfile selects federation versus absorption; there is no single integration pattern.
  • Identity has strong precedent, navigation partial precedent, and settings absorption is the largest unknown.

What it owns

  • Host session and tenant contract
  • Settings scopes and mounting
  • Navigation registry
  • Onboarding ownership
  • Branding and account surfaces
  • Permission and audit context

Open first-principles questions

  • What is Actionist’s canonical host contract?
  • Can settings/navigation be declarative?
  • Which donor routes must be unreachable?
  • How are capability permissions represented consistently?

  • Capability host requirements

1Settings registry with hierarchy, schema and override provenance—The one real mechanism P10 should build: a hierarchical settings tree (system to tenant to workspace to user) where every resolved value carries the level and principal that set it, and the schema generates its own UI, validation and API surface from one declaration.inferredtop10—
2Navigation registry synthesizing Luigi's node schema with Backstage's contribution model—Nodes with label, icon, route, ordering, owner and a permission predicate, contributed by modules rather than edited into the shell, resolved at runtime from a manifest rather than at build time.observedtop10—
3Route-ref indirection so modules link without knowing paths—Opaque route targets bound to concrete paths once at startup, letting modules link to each other without knowing any concrete path including their own, with bindings explicitly disableable.observedtop10—
4Two-token exchange with sealed host claims as the only guest identity path—The long-lived credential never leaves the host backend and never appears in a query parameter; a short-lived audience-bound single-use token crosses the boundary carrying entitlement and tenant facts as signed claims, so donors never query a host API and nothing can be forged.observedtop10—
5Nav visibility predicate unified with the authorization check—A nav node's visibility is the same evaluation as its route guard, so the two can never drift, with a debug view reporting which gate denied.inferredtop10—
6Cascading emptiness as a host guarantee—An entitlement-stripped module takes its nav entry and any now-empty parent group with it, so absorption never leaves empty chrome behind.observedtop10—
7Explicit per-node settings combination mode—Make the conflict rule a first-class field on each settings node with the safe mode as default, rather than a global convention.observedtop10—
8Absorption manifest declaring chrome suppression and route reconciliation—The manifest names which donor header, sidebar and settings links are hidden, and the host publishes its prefix while the guest acknowledges its route table so deep links are validated before they break.inferredtop10—
9Structurally narrow-only role delegation—A tenant-defined role is constrained by construction to a subset of its parent, rather than reviewed into compliance after the fact.observedtop10—
10One module declaration feeding both registries—A settings schema declares which nav node surfaces it, so a new module's settings page appears in the right place with no host edit; the same manifest carries nav contributions and required permissions.observedtop10—
11Runtime nav registration rather than deploy-time only—Donors are absorbed continuously, so registration must be possible at runtime.observedregister—
12Schema-validated nav manifest at write time—Validate the nav document on write, closing the silent-failure class.observedregister—
13Absorption-time capability negotiation—The donor declares which identity lanes it supports and the host selects one, instead of hand-porting every donor to a single lane.inferredregister—
14Settings provenance exposed in the UI—Show which scope supplied a value and which rule won, answering why is this value what it is.observedregister—
15Nested navigation beyond one flat level—A real gap rather than a nicety: donors with genuine sub-hierarchies cannot be represented flat.observedregister—
16Nav and settings registry diffing as an upgrade gate—A module upgrade surfaces exactly which nav entries and settings keys it adds, removes or renames.inferredregister—
17Resolved settings as policy input—Feed resolved settings into the policy engine as data so configuration and authorization share one evaluation path.inferredregister—
18Tenant-scoped identity isolation as an explicit switch—Whether a user identity is shared across tenants or scoped to one must be a deliberate setting, not an assumed default in either direction.observedregister—
19Record ephemeral guest membership—Embedded guest users holding permissions only for a token's life and never appearing as members is an audit blind spot that must be recorded deliberately.observedregister—
20Headless identity with host-owned UI as default posture—The host never surrenders its design system to an IdP's screens.observedregister—
21Branding and provider inheritance as a settings subtree—A tenant's theme, auth providers and login surface are one inheritable subtree rather than scattered configuration.observedregister—
22Directory reconciliation from an events log with a replayable cursor—Prefer a replayable event cursor over webhooks for directory sync.observedregister—
23Progressive settings depth as a per-module property—A donor exposes a curated subset by default and its full surface on request, with the schema carrying an audience level.observedregister—
24Mounting-layer refinements—Extension slots as a permission surface rendering only contributions the principal may see; runtime enable/disable of mounted modules for staged rollout; session propagation across the microfrontend boundary as a defined contract; tenant-scoped nav trees driven by the tenancy model rather than branching in module code.inferredregister—
