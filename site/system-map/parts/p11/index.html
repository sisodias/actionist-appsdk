What we learned

Current synthesis from the research packet. Exact records and complete source artifacts remain visible below.

Research conclusions

  • Borrow OAuth machinery, catalogues, durable execution and authorization engines.
  • Own tenant-keyed connections, outbound token brokerage, idempotency, egress refusal and the action ledger.
  • Callers pass identity and intended action, never raw provider secrets.

What it owns

  • Provider/action/trigger catalogue
  • OAuth and credential setup
  • Tenant connection store
  • Retries, idempotency and rate limits
  • Approval and action receipts

Open first-principles questions

  • Canonical provider/action schema?
  • Which popular providers need scripted setup?
  • How does browser operation fit?
  • What is the authority/approval model for side effects?

  • Tenant authority
  • Secrets

1Server-side idempotency keyed per tenant and connector with request fingerprinting—The highest-consequence must-build. Key store, SHA-256 request fingerprint so a reused key with a mutated payload is a hard error, optimistic locking for concurrent replays, TTL, and an explicit replay receipt header. Every action declares its idempotency class and the runtime refuses to auto-retry the unsafe class, defaulting to unsafe when undetermined.observedtop10—
2Idempotency layer positioned inside the rate limiter and auth check—Ordering is load-bearing, not an implementation detail. If the rate limiter runs first, a throttled request can produce a different result under the same key, and the key's safety guarantee silently does not apply.observedtop10—
2Outbound token broker with per-tenant-per-connector custody—Storage, auto-refresh, rotation and instant revocation for many long-lived third-party tokens. The caller passes an identity, never a secret; the broker injects credentials server-side so generated app code and model context never hold a third-party token. Refresh 15 minutes early under a lock keyed by tenant and connection, discriminating invalid_grant (user's problem, mark the connection ERROR) from invalid_client and invalid_scope (our bug, must not mark the connection bad).observedtop10—
3Tenant-keyed connection store with per-tenant key derivation—Tenant column from the first migration, per-tenant key derivation, stable externalId as the reference rather than a UUID or display name, envelope encryption with AAD asserting purpose and app so a wrapped key cannot be replayed elsewhere.observedtop10—
4Dry-run as a non-disableable first-class action mode—Return the exact resolved outbound request that would be sent, with empty results and no side effect, on by default and forceable by the action author so a tenant cannot disable it.observedtop10—
5Unified per-tenant action-attempt ledger—Every attempt, retry, idempotency replay, policy denial and approval in one queryable trail, with receipts that deliberately exclude payload bodies.inferredtop10—
6Egress allow-list derived from the connector manifest and bound to an enforcing proxy—Supply the enforcement half that policy engines lack, with live revocation so disabling a connector takes effect immediately rather than at cache expiry.observedtop10—
7Named connection selection with no ambient authority—When a tenant holds several accounts for one provider, the action must name which connection it uses. Silent selection is a defect class.observedtop10—
8Consent graded by consequence with policy on action payload—Three tiers (read, reversible, irreversible-or-financial) defaulting to the middle, with policy evaluated over the payload itself (amount, recipient, record count) and a human-approval branch above a per-tenant threshold, expressible as a composable workflow step.observedtop10—
9Browser connectors as a separate authority class—Browser automation must not inherit the API connector's authority model, because its credential is a replayable session blob rather than a scoped token.observedtop10—
11Per-tenant-per-connector fair-share rate limiting with provider-signal backoff—One tenant cannot exhaust a shared third-party quota; backoff honours Retry-After and observed 429 rates per connector rather than a fixed exponential curve.observedregister—
11Effectively-once composition—Transactional outbox for delivery plus a consumer-side idempotency gate, since at-least-once delivery alone never reaches once.inferredregister—
12Signed connector manifests with provenance checked at load—Fill the trust gap the MCP registry leaves open.observedregister—
13Capability-binding execution with tiered sandbox selection—No ambient network or filesystem, only injected capabilities; sandbox tier selected per action from its manifest (isolate for trusted, gVisor for semi-trusted, microVM for arbitrary).observedregister—
14Webhook ingest with signature verification and operator-triggered replay—Durable capture of inbound callbacks with replay, covering the half Svix does not.observedregister—
15Durable execution as an embedded library rather than a server—Keep the runtime deployable as one artifact by preferring a library-shaped durable-execution engine over a server with its own persistence and matching tiers.observedregister—
16Catalogue state flags so a listed integration is never mistaken for an executable one—Keep catalogue-only, needs-credential and locally-executable distinct, enabling a large browsable catalogue where only some entries are wired without lying to the agent about what it can call.observedregister—
17Generated setup forms from constrained provider schemas—Render every connector's credential step from data rather than maintaining one component per connector.observedregister—
18Scope-aware action gating—Surface per-action requiredScopes against the connection's grantedScopes to enable reconnect-with-more-scopes, and capture a CredentialProfile at connect time so the UI can say who an action runs as without exposing the token.observedregister—
19Fail fast on ambiguous or unsafe configuration—Refuse to boot on mutually exclusive credential configuration rather than silently choosing, and never degrade to plaintext storage.observedregister—
20Connect-session token with origin-checked postMessage handshake—Server mints a short-lived token scoped to allowed integrations per customer; the iframe is created without the token in the URL, the child posts ready, the parent verifies event.origin and only then posts the token, keeping secrets out of browser history, referrers and access logs.observedregister—
