What we learned

Current synthesis from the research packet. Exact records and complete source artifacts remain visible below.

Research conclusions

  • Rollback is multi-object across artifact, configuration, data/schema and routing horizons.
  • Every capability needs stable identity, version, trace context, owner and machine-readable health.
  • ComputeSDK cannot be the load-bearing abstraction when memory-preserving pause is required.

What it owns

  • Package/microfrontend/service/worker runtime profiles
  • Preview isolation
  • Build, contract, visual and workflow tests
  • Deployment and subdomains
  • Version pinning, recovery and rollback

Open first-principles questions

  • Which runtime profiles are v1?
  • What sandbox/deploy infrastructure should be rented?
  • How are failures attributed per capability?
  • Can blocks upgrade independently?

Inputs

  • AssemblyPlan
  • Packaged assets
  • Host bindings
  • Acceptance fixtures

Outputs

  • QualificationDossier
  • ReleaseManifest
  • Deployment
  • RollbackPlan

Explicit holds and blockers

  • Account-wide usage limit terminated survey wave 1 across all six subagents; BLOCKED not FAIL.
  • Commercial/OSS denominator shortfalls recorded per survey; no padding.
