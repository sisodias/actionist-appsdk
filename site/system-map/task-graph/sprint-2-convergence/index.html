# Sprint 2 convergence — the Actionist modular assembly framework

Date: 2026-08-27  
Verdict: `converged_with_holds`  
Boundary: research-only, `UNEXECUTED`, `NOT_ADMITTED`, admitted modules/blocks `0`

## Executive result

Sprint 2 produced a coherent framework for turning heterogeneous software supply into composable Actionist applications. The central conclusion is that Actionist should not attempt a universal “repo converter.” It should identify a capability, choose its reuse shape, declare its host bindings, eliminate incompatible compositions deterministically, and produce a decision packet for the few choices automation cannot safely make.

The framework is:

```text
ProductSpec
  -> discover source containers
  -> identify capability boundaries
  -> choose reuse shape
  -> declare seven linked module records
  -> predict normalization surgery
  -> bind data / identity / navigation / settings / tokens / connectors / runtime
  -> deterministically eliminate incompatible assemblies
  -> human/model judgment only among feasible alternatives
  -> qualify each binding and the complete workflow
  -> release with multi-object rollback
  -> learn from attributed production evidence
```

## 1. What the reusable unit is

A repository is a source container. The reusable unit is a **capability in a declared reuse shape**, joined to a particular Actionist host through a BindingPlan.

The architecture axis is `reuse_shape`:

- intact service;
- embedded module or microfrontend;
- transplanted subsystem;
- extracted package;
- adapter around an external system;
- generated pattern;
- template/archetype;
- custom delta.

This must remain separate from `rights_exposure`, which describes how much source is copied or derived. Earlier artifacts mixed these two axes and produced contradictory “shape” enums.

## 2. The seven-record contract family

One giant Block Contract is replaced by linked records:

1. `CapabilityContract` — what the capability provides, requires and can affect.
2. `PackagingProfile` — reuse shape, source identity, dependency closure and upstream synchronization model.
3. `HostContract` — identity, tenancy, data, navigation, settings, token, connector and runtime capabilities offered by Actionist.
4. `BindingPlan` — how this capability binds to this host and which normalization surgeries are required.
5. `QualificationDossier` — evidence at a pinned artifact/environment, min-gated T0–T4.
6. `RegistryRecord` — durable identity, versions, dependencies, compatibility and lifecycle.
7. `ReleaseManifest` — exact deployed composition, runtime profile, evidence, rollback objects and recovery horizon.

These records are linked, not fused. Capability semantics do not mutate because one deployment used a different runtime. A later green qualification receipt does not retroactively make an old artifact green.

## 3. Repo-to-module is prediction plus decision, not conversion

P04 identified 28 normalization surgeries across 14 concerns:

- branding;
- onboarding;
- identity;
- tenant handling;
- settings;
- navigation;
- data ownership;
- migrations;
- events;
- connectors;
- token mapping;
- runtime;
- upgrade;
- rollback.

Only 7 are fully deterministic, 17 are semi-automatic and 4 require named human decisions. Three are cosmetic, 13 boundary-level and 12 architectural; six are irreversible.

The three irreducible decisions are:

1. reuse shape;
2. migration/data authority;
3. admission.

The output of automation is therefore a cheap elimination pass plus a decision packet. It is not “converted repo ready for production.”

Reuse shape predicts the surgery set before source is deeply read. The three worked traces touched 7, 14 and 6 of the 14 concern categories respectively, confirming that an intact service, transplant and engine-plus-owned-delta require structurally different work.

## 4. Mounting, theming and editing share one mechanical cause

P07 and P08/P13 independently converged on **cascade and session coupling** as a primary feasibility axis.

A cross-origin iframe is a hard CSS and session boundary. It can preserve a donor cheaply, but cannot honestly promise native theme parity or arbitrary host editing. In the measured SISOCRM estate:

- framed preservation required roughly 17–62 patch lines;
- native absorption required 273 lines across 9 files and touched authentication strategy, SSR, database provider and a donor public-API validation regex.

This falsifies “adaptation is always 1–2%” as a universal claim. It may be true for a framed donor and badly false for a native absorption.

Five visual-binding classes are now explicit:

1. native token emission;
2. source extraction and retokenization;
3. scoped variable bridge;
4. scoped stylesheet override;
5. frame negotiation.

Theming is an input to reuse-shape selection, not a cosmetic step after it. The same mount fact determines which edit operations are possible. A theme operation on a cross-origin framed donor must be denied or deliberately downgraded, not silently approximated.

## 5. The deterministic composer

P12 defines 22 ordered rules across seven phases, representing 19 distinct constraints. Ordering is load-bearing because the first failing rule names the next gate.

The composer returns exactly three verdicts:

- `FEASIBLE`;
- `INFEASIBLE`;
- `UNDERDETERMINED`.

`UNDERDETERMINED` is a contract-defect report, never model uncertainty. It names the missing field, why it matters, who must provide it and whether it blocks promotion. The solver applies zero relaxations. A model cannot average or explain away a failed identity, tenancy, migration-owner, rollback, evidence or authority constraint.

The 24 fixtures currently resolve to:

- 2 feasible;
- 15 infeasible;
- 5 underdetermined;
- 2 process-property fixtures;
- 3 held-out;
- 3 zero-tolerance.

The next credible dry run is to encode three real P03 shelf candidates in the seven-record family and hand-execute all 22 rules. That requires no source execution, model run, client data or admission.

## 6. Runtime, release and learning

Runtime profile is selected from ownership and lifecycle requirements, not deployment convenience. The five current profiles are:

- package in host;
- microfrontend;
- sidecar/service;
- worker;
- scheduled job.

Every capability requires stable identity, version, trace context, owner and machine-readable health. Attribution is classified as dependency, service, endpoint, deploy or none. `none` is inadmissible; deploy-level evidence may never demote a specific capability.

Rollback is not a boolean. The canonical eight rollback objects are:

1. `code_artifact`;
2. `configuration`;
3. `secrets`;
4. `database_schema`;
5. `data`;
6. `donor_revision`;
7. `surface_route`;
8. `connector_credential_state`.

The composition recovery horizon is the minimum horizon across required rollback objects. An uncomputable horizon is `0`, which refuses release by arithmetic. Unrecoverable external effects are recorded separately; they do not falsely turn every notification job into an impossible rollback object.

Learning consumes attributed quality, contract-defect, environmental and operational signals. Only quality evidence changes capability ranking. A revoked OAuth grant is environmental; `UNDERDETERMINED` is a contract defect. Correlated failures count once, and silence never retires a capability.

## 7. Coordinator convergence decisions

The following seam decisions are canonical for the next experiment:

### C-S2-01 — ReleaseManifest ownership

P14's ReleaseManifest schema is the canonical superset. It imports P04 identity, packaging, qualification and registry references. P04's embedded ReleaseManifest remains the semantic source but must not become a second runtime schema.

### C-S2-02 — authority

`CapabilityContract.authority_class` is a summary. Each port's `external_effect` is authoritative. The stricter value wins; disagreement returns `UNDERDETERMINED` and must be repaired at the contract source. Session authority remains a separate ladder: read, stage, write, message, deploy.

### C-S2-03 — staged bindings

Add `BindingPlan.lifecycle_state = planned | prepared | staged | active | retired`. `staged` means the complete binding exists with no tenant-visible external effect. It is not a capability authority class and must never imply execution evidence.

### C-S2-04 — host identity

The HostContract must state `identity_source = host_verified_context`. Client-supplied identity or tenant headers are untrusted input unless produced and signed/verified by the host identity boundary. Failure is inadmissible, not a style warning.

### C-S2-05 — evidence tiers

Use P04's canonical T0–T4 enum. P14/P15 must include T0. Promotion remains the minimum across every required evidence family; absent families cannot raise a tier by omission.

### C-S2-06 — rollback vocabulary

Canonical spellings are the eight names in §6. Aliases `config`, `schema` and `connector_state` normalize to `configuration`, `database_schema` and `connector_credential_state` at ingestion only.

### C-S2-07 — correlated failures

Add `failure_cause_group_id` to the binding/release evidence path. Signals from one cause group count once for ranking/demotion. Grouping belongs to the release/binding record; a signal references it rather than inventing it.

### C-S2-08 — upgrade evidence

`PackagingProfile.upstream_sync_model` is required input to ReleaseManifest and learning evidence. A vendored capability with no declared upstream model cannot silently emit “no upgrade failures.”

### C-S2-09 — glue budget

Replace one global line ceiling with a budget by normalization-surgery cost class: cosmetic, boundary and architectural. Irreversible surgeries require a named human gate regardless of apparent size.

## 8. What remains unproven

- No source was converted, mounted, composed, built, deployed, released or rolled back.
- No module has passed admission.
- Settings absorption has zero direct precedent in the 33-surface commercial survey; v1 should keep donor settings rendered behind host navigation unless a pilot proves otherwise.
- The host navigation registry is build-not-adopt: Luigi has a useful data structure and Backstage has a contribution model, but neither supplies the required combination.
- The built estate has no host tenant switcher; Teable's space switcher remained visible to cover that authority hole.
- Corpus-wide theme eligibility and visual quality remain unmeasured.
- Whether clients accept bounded editing remains unknown.
- Cross-client learning consent remains unknown and gates the cross-client premise.
- Five runtime profiles may be insufficient; cross-origin iframe ownership is the likeliest falsifier.
- Real adaptation cost remains unknown beyond the small measured donor sample.

## 9. Recommended next experiment

Do not begin a full client build and do not rank another thousand repositories.

Run a **three-candidate contract-and-solver pilot**:

1. choose three real P03 candidates representing intact service, transplanted surface and engine-plus-owned-delta;
2. write the seven records for each without copying or executing source;
3. derive their normalization-surgery sets;
4. hand-run the 22 composer rules;
5. test the nine coordinator seam decisions above;
6. record missing fields, contradictory evidence, human decision count and estimated glue by cost class;
7. stop before implementation and choose one candidate only if the framework produces a coherent, bounded plan.

That experiment tests whether the framework can describe real supply. Only after it passes should Actionist authorize one staged, read-only module binding.
