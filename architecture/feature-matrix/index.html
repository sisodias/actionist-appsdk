The headline

Lovable's surface is 110 features. Our scope deletes 19 outright — and 16 of those are rated hard or very‑hard (post Opus audit; connectors reclassified as real, phased work). The scope isn't a discount on effort; it's a discount on the hardest effort. What vanishes is the whole backend-provisioning and connector estate: Lovable Cloud, the ~100-connector catalog, RLS, secrets, Stripe/Paddle, security scanning — because the platform already owns the database, the policies and the deploy target.

Cena is right that Lovable is near-impossible to replicate in general. He's wrong for his own case, and this is by how much.

The four gaps — where you build, not rob

Nothing in the 500-repo pool solves these. This is the most valuable output of the exercise.

NO ANSWER IN 500 REPOS 5. data layer over platform-owned Postgres

NO POOL REPO implements row security for GENERATED apps over a platform-owned Postgres. Doable's views (075_vigil_sandbox_views.sql) are platform observability (v_sandbox_posture, v_sandbox_oom_7d), not tenant query constraints. No pool repo shows an agent authoring RLS policies safely. chef avoids the problem by never letting the model write schema, which presumes Convex.

Steal: Nothing available — must be designed. Closest pattern is chef's 'model writes handlers in a blessed dir where identity comes from a platform helper, never raw queries'.

NO ANSWER IN 500 REPOS 7. deploy: hosted publish, wildcard subdomains, DNS/TLS

NO POOL REPO automates registrar/DNS record provisioning or domain-ownership verification. sandboxd solves wildcard TLS + routing for *previews*; Doable models custom_domains as rows. The step between 'user types their domain' and 'certificate served' is unimplemented in the pool.

Steal: Nothing available. Note that per-customer custom domains DO need per-host ACME, so sandboxd's wildcard trick does not extend to them — that is a separate cert path.

NO ANSWER IN 500 REPOS 2. sandbox/preview runtime

NO POOL REPO provides a provider-abstracted sandbox layer that swaps E2B / Modal / Daytona / WebContainers behind one interface. The pool holds only consumers and consoles: e2b-dev/dashboard (Apache-2.0, management UI, no runtime), e2b-dev/desktop, Automata-Labs-team/code-sandbox-mcp (MIT but pushed 2025-03-23, stale).

Steal: Nothing available. sandboxd's sandboxspec/ + manifest/ (sandbox.yaml with web.command/port/health_path) is the closest thing to a provider-neutral run contract and is the right shape to generalise.

NO ANSWER IN 500 REPOS 6. multi-tenancy + secret isolation

Lane 6 has no single winner covering both halves. Doable owns per-tenant DATA keys (workspace_keys envelope encryption at rest); sandboxd owns RUNTIME secret isolation (authproxy so credentials never enter the workspace, AES-256-GCM config sealing, fail-closed nftables egress). Adopt BOTH; neither alone is sufficient.

Steal: Doable's workspace_keys schema + sandboxd's authproxy, together.

Why the RLS gap is the sharp one

The teardown identified platform-owned schema+policies as our advantage — it removes Lovable's worst production risk, LLM-authored RLS on a public database. It turns out nobody in open source has built it. So the thing that makes the scoped version safer than Lovable is also the thing you must design from scratch. chef sidesteps it by never letting the model write schema, which presumes Convex.

The licence trap

Of the 38 Lovable-class clones in the corpus, only 20 can be code sources. The rest are default-copyright or copyleft — architecture reference only.

The famous ones are the least usable:

  • dyad — 21,322★, NOASSERTION + FSL src/pro → STUDY
  • beam-cloud/lovable-clone — closest to Actionist's MCP surface, no licence at all → STUDY
  • sa4hnd/vibra-code — AGPL-3.0, viral → STUDY

Only 5 of the 38 clones scored into any capability lane. The best implementations live in serious infrastructure repos, not clone repos — which is why scoring all 500 rather than just the 38 was the right call.

Composition verdict, all five permissive: chef loop discipline + sandboxd runtime/secrets/TLS + Doable tenancy schema + astryx vibe-test harness as the Block Contract eval proof + dyad src/version_preview/ (Apache-2.0 files only).

Architecture: TypeScript for v1, not Rust

Sampled twice independently — main session drew a random 45 of 302 permissive repos (TypeScript 14, Python 9, Go 4, Rust 3); the architecture lane drew a stratified 45 (TypeScript 12, Rust 3). Different method, same shape.

"Probably Rust" and "rob it first" are mutually exclusive for v1, and rob-first is the more valuable half — a Rust v1 hand-writes what the corpus would otherwise hand you. Rob-first-rewrite-later works per subsystem, never globally. The rewrite trigger must be a measured SLO failure on a contract-stable subsystem that renting and ordinary optimisation can't fix. No such measurement exists today, so no Rust rewrite is justified today.

Caveat: 45-of-302 supports "TypeScript-dominant". It does not support a percentage. Don't let anyone quote it as one.
