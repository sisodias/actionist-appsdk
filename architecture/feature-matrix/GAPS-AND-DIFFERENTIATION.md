# Gaps and differentiation

**Research date:** 2026-08-27  
**Scope:** Actionist client-facing builder: platform-owned Postgres, constrained app shape/design system, generated apps on `actionmodel.com` subdomains, and low-cost per-build generation.  
**Evidence convention:** `DIRECT` means observed in the cited source or command output. `INFERRED` means a conclusion drawn from those observations. A claim not directly evidenced is marked `UNVERIFIED`.

## Executive answer

Actionist should not compete with Lovable on general-purpose code generation. The defensible boundary is a controlled application factory: platform-owned data contracts, tenant-aware access mediation, schema compatibility gates, reversible releases, and a benchmark that scores live behavior rather than screenshots. This scope deletes Lovable's LLM-authored-RLS and connector burden, but it concentrates risk in one shared platform database: one schema or authorization mistake can affect every generated client app at once.

## B. Problems created by Actionist's scope

### B1. Multi-tenant isolation over one platform Postgres — the highest-risk issue

**DIRECT:** AWS's SaaS Lens calls tenant isolation foundational and says crossing a tenant boundary can be a significant and potentially unrecoverable SaaS event ([AWS SaaS Lens: Tenant Isolation](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-isolation.html)). PostgreSQL documents that row policies can default-deny, but table owners and `BYPASSRLS` roles bypass them unless forced; it also documents that view ownership/invoker settings determine whose policies and permissions apply ([PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html)).

**INFERRED:** A client app must never receive a platform-wide database credential, and generated SQL must not select directly from shared tables. The safest v1 boundary is a platform-owned gateway or a fixed catalog of `security_barrier`/`security_invoker` views with tenant identity supplied from a server-validated session, plus deny-by-default tests. Per-client view names alone are not isolation: they can still expose excess columns/rows, and ownership/BYPASSRLS mistakes can defeat policy.

Required controls:

- tenant identity comes from authenticated server context, never a browser-supplied `tenant_id` accepted as authority;
- generated apps call typed platform endpoints or allowlisted views/procedures only;
- service roles are split by operation and cannot be used by generated frontend code;
- every release runs cross-tenant read, write, IDOR, and timing/error-disclosure tests;
- platform schema and policy changes require compatibility review and canary rollout.

### B2. Per-client scoped views and permissions

**DIRECT:** PostgreSQL says a `security_barrier` view is needed when a view provides row-level security, and that view/RLS behavior changes with `security_invoker`; security-barrier views also impose performance tradeoffs ([PostgreSQL rules and privileges](https://www.postgresql.org/docs/current/rules-privileges.html)).

**INFERRED:** The scope creates a control-plane/data-plane problem Lovable's ordinary single-project model does not face: Actionist must maintain a catalog mapping `{client app, tenant, role, operation, columns}` to stable views or typed procedures. View generation must be migration-managed, audited, and revocable. A single shared role is operationally simple but weakens blast-radius control; per-client database roles improve isolation but increase connection, secret, and migration complexity. Prefer a gateway plus stable platform roles in v1; use database roles as a defense-in-depth layer, not as the sole policy.

### B3. Wildcard subdomain DNS and TLS at scale

**DIRECT:** Cloudflare documents wildcard DNS as useful when hundreds or thousands of subdomains point to the same resources, with exact records taking precedence; its Universal SSL covers first-level subdomains but deeper wildcards require separate coverage ([wildcard DNS](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/)). Let's Encrypt documents that wildcard certificates require DNS-01 rather than HTTP-01 and rely on `_acme-challenge` TXT records ([challenge types](https://letsencrypt.org/docs/challenge-types/)).

**INFERRED:** This is new operational surface for Actionist: hostname claim/uniqueness, tenant-to-host routing, certificate issuance/renewal, preview-vs-production hostnames, abuse controls, and DNS failure observability. Use one wildcard edge certificate where the hostname depth allows it, terminate TLS at a managed edge, route by signed host mapping, and reserve deeper hostnames only when their certificate lifecycle is automated and tested.

### B4. Noisy-neighbour risk on shared sandbox/build infrastructure

**DIRECT:** Kubernetes documents that teams sharing a fixed-node cluster can exceed their fair share, and ResourceQuota limits aggregate namespace compute, storage, and object consumption; quota violations can be rejected with HTTP 403 ([Kubernetes ResourceQuota](https://kubernetes.io/docs/concepts/policy/resource-quotas/)).

**INFERRED:** Renting sandbox execution deletes fleet ownership but not fairness or abuse. (**[updated post gap deep-dive 2026-08-27]** This originally read "E2B/Modal/Daytona"; Daytona is disqualified — unmaintained since June 2026, no licence on the current tree. See `GAP-DEEP-DIVE.md` GAP 3. The fairness argument is vendor-independent and unaffected.) Actionist still needs per-build CPU, memory, wall-clock, concurrency, network-egress, disk, and model-call budgets; queue priority must not let one client starve others. Isolate preview execution from production serving, and terminate idle/runaway processes deterministically.

### B5. Who pays for a runaway client app?

**DIRECT:** Lovable's docs say one credit balance covers build, hosting/backend, and deployed-app AI usage, and that services pause at zero balance ([credits docs](https://docs.lovable.dev/introduction/credits-and-usage)). Stripe documents usage alerts and thresholds but notes that hard spend limits generally require application-side enforcement ([usage alerts](https://docs.stripe.com/billing/subscriptions/usage-based/alerts-and-thresholds)).

**INFERRED:** Actionist needs an explicit payer and kill policy before launch: default build budget, runtime quota, owner-visible ledger, alert thresholds, hard stop, and an emergency platform circuit breaker. “Cheap per build” cannot mean uncapped runtime liability. The platform should remain protected even when a client leaves, loses payment, or ships an accidental polling loop.

### B6. Supporting non-engineers after they leave

**INFERRED:** This is a lifecycle/support problem created by the client-facing scope, not a Lovable generality problem. The durable unit is not source code alone: it is the app manifest, data contract, generated artifact, access/deployment history, owner/admin roster, support runbook, and rollback point. Require organization ownership rather than an individual's account, transfer/offboarding, dependency/license manifest, generated-app health checks, and a support-safe “freeze” mode that prevents ad-hoc mutation while preserving service.

### B7. Platform schema migration breaking N generated apps simultaneously — severe shared blast radius

**DIRECT:** PostgreSQL's `CREATE VIEW` and RLS documentation establishes that views/policies depend on underlying relations and permissions ([CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html), [row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). **UNVERIFIED:** the exact current PostgreSQL error/lock behavior for every destructive `ALTER TABLE` variant was not established in this pass; do not rely on assumed dependency semantics.

**INFERRED:** This is the most important Actionist-only risk. In Lovable, one project commonly owns its schema; in Actionist, the platform schema is a shared ABI for N generated apps. A rename, type change, removed column, changed enum, altered nullability, policy change, or semantic change can break many deployed clients at once, even if every generated app's code is unchanged. Treat the platform schema as a versioned public API:

1. expose additive, stable view/procedure contracts rather than base tables;
2. attach each app to a contract version and maintain old versions during a deprecation window;
3. use expand → dual-read/dual-write where needed → backfill → migrate clients → contract tests → contract removal;
4. run generated-app compatibility tests against a migration candidate before production;
5. canary the migration against representative tenants/apps and monitor errors/latency;
6. make rollback mean restoring the prior contract or forward-fixing data, not pretending code history can restore shared production data;
7. maintain an inventory answering “which apps depend on this field/procedure?” before approval.

The product implication is direct: schema compatibility and migration orchestration are not backend chores; they are a core differentiator and a prerequisite for safely serving many client apps.

### B7: the schema-migration ABI argument — stress-tested, and it survives with a correction

**Verdict: the risk survives. The mitigation is real prior art, but the doc overstates how
far that prior art carries.**

Two things changed under audit.

**1. The UNVERIFIED hedge in B7 can be discharged, and it strengthens the argument.** B7
says "the exact current PostgreSQL error/lock behavior for every destructive `ALTER TABLE`
variant was not established." It now is, for the variant that matters. Per
[ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html): `RESTRICT` is
the default and will "Refuse to drop the column or constraint if there are any dependent
objects"; you "need to say `CASCADE` if anything outside the table depends on the column,
for example, foreign key references or views." The same page: "An `ACCESS EXCLUSIVE` lock
is acquired unless explicitly noted."

This cuts both ways and both ways favour the B7 thesis. The default RESTRICT is a genuine
safety net — a `DROP COLUMN` under a contract view fails loudly rather than silently
breaking N apps. But `CASCADE` **drops the dependent views themselves**, so a single
careless `CASCADE` destroys the contract layer for every app pinned to it, and the
`ACCESS EXCLUSIVE` lock means the operation blocks all readers while it runs. The control
B7 needs is therefore narrower and more concrete than "compatibility review": **prohibit
`CASCADE` on any relation carrying a live contract view, and make that a mechanical gate,
not a review checklist.**

**2. The versioned-view mitigation has direct, shipping prior art — with a hard limit the
doc does not account for.**

| Tool | Receipt | Mechanism |
|---|---|---|
| `xataio/pgroll` | `gh api repos/xataio/pgroll` → `xataio/pgroll  6561  Apache-2.0  2026-08-19T06:03:51Z` | "creating virtual schemas by using views on top of the physical tables"; clients pin a version with `SET search_path TO 'public_initial_migration'`; expand/contract with triggers syncing writes between old and new columns |
| `fabianlindfors/reshape` | `gh api repos/fabianlindfors/reshape` → `fabianlindfors/reshape  1850  MIT  2026-08-04T12:45:48Z` | "creating views that encapsulate the underlying tables, which your application will interact with"; clients pin via `SET search_path TO migration_1_initial_migration`; three-phase start → rollout → complete, with `abort` to undo |

Two independent tools converging on the same mechanism — versioned schemas of views, client
pinning by `search_path` — is strong evidence the B7 mitigation is workable rather than
invented. **So the answer to "is the versioned-view contract actually workable with
generated apps pinned to contract versions?" is yes, and it is the industry answer.**

**But the doc's step 2 — "attach each app to a contract version and maintain old versions
during a deprecation window" — assumes more than the prior art delivers.** Per
[pgroll internals](https://xata.io/blog/pgroll-internals): pgroll "keeps two versions of
your schema active at the same time during a migration; the old schema and the new," and
after completion "only the most recent schema is available." One migration at a time, two
versions, then collapse. Reshape is the same three-phase shape.

That is a migration-window tool, not a long-lived multi-version contract registry. Actionist's
scope is harder: N generated apps upgrade on **their owners' schedules**, not on a
coordinated rollout the platform controls, so the deprecation window is measured in months
and the number of simultaneously-live contract versions is unbounded rather than two. Neither
tool solves that. The gap between "two versions during a controlled rollout" and "K versions
across independently-owned client apps" is real, and it is Actionist's to build.

Three further caveats from the prior art that B7 should inherit:

- **`search_path` is session state.** A transaction-pooling connection pooler can hand an app
  a connection whose `search_path` does not match its pinned version. Version pinning must be
  re-established per physical connection, or enforced somewhere other than session state.
- **Default `search_path` silently bypasses the contract.** If unset, Postgres resolves to
  `public` and the app reads base tables directly — the contract layer is not
  fail-closed by default. This has to be inverted for Actionist: generated apps must have no
  route to base tables at all, which the B1 gateway/role split already implies but B7 does not
  state.
- **View-based versioning has known expressiveness limits.** Constraint visibility through
  the versioned views is a documented open problem in pgroll, discussed as unfixable without
  abandoning views ([xata.io](https://xata.io/blog/pgroll-5k-stars-on-github)).

**Net effect on B7:** the severity rating stands and the direction of the mitigation is
confirmed by prior art. Steps 1, 3–7 survive as written. Step 2 needs the correction above:
maintaining K long-lived contract versions across independently-upgrading client apps is
beyond what pgroll or Reshape provide, so it is a build item with a known ceiling, not a
solved problem to adopt.
