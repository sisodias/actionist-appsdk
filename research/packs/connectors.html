AM-CONNECTORS / detailed resource room

We don't have to build a hundred connectors. We have to choose which catalogue we're allowed to host.

The connector problem was scored ZERO in the 26 Aug Lovable teardown on the reasoning that "the platform already owns the DB". That is true of Actionist's own Postgres and false of everything a client dashboard wants to touch. This room corrects that, and answers the real question: can we import a catalogue instead of hand-writing integrations? Yes — with a licensing trap in front of it that would have cost real money.

01 / Mechanics

How a connector actually works

Verified by running OpenConnector locally, not read from docs

A "connector" is three separable things that vendors sell as one: a catalogue entry (declarative facts about an API), a credential vault (encrypted per-user tokens plus refresh), and an execution proxy (an authenticated call). Once you see them apart, most of the build shrinks — and it becomes obvious which parts we can take and which we must own.

01 CATALOGUEDeclarative factsAuth URL, token URL, scopes, pagination style. Pure data — no code. This is what we import instead of writing.
02 CONSENTUser clicks connectWe build an authorize URL from the catalogue entry and redirect. The user approves scopes at the vendor.
03 EXCHANGECode → tokenVendor redirects back with a code; server swaps it for access + refresh tokens using our client secret.
04 VAULTEncrypt & storeAES-GCM at rest, keyed per tenant. Refresh early under a lock. This layer is ours.
05 EXECUTEAuthenticated callDecrypt at call time, inject the header, proxy to the vendor. The generated app never sees a token.
The load-bearing insight: steps 1–3 and 5 are commodity — they are the same shape for every vendor and are already written, tested, and permissively licensed in open source. Step 4 is the only part that must be ours, because it is where multi-tenancy lives, and no OSS gateway we found does multi-tenancy. That is not a gap in the research; it is the actual work item.

A catalogue entry is genuinely just data. This is Slack, from OpenConnector's src/providers/slack/definition.ts — every fact needed to render a connect button and complete a handshake:

// nothing here is bespoke code — it is a typed record service: "slack" authTypes: ["oauth2"] auth: [{ authorizationUrl: "https://slack.com/oauth/v2_user/authorize" tokenUrl: "https://slack.com/api/oauth.v2.user.access" refreshTokenUrl: "https://slack.com/api/oauth.v2.access" scopeSeparator: "," tokenEndpointAuthMethod: "client_secret_post" }]

Multiply that by 1,445 and you have the catalogue. The fiddly fields — refreshTokenUrl, tokenEndpointAuthMethod, scopeSeparator — are exactly the per-vendor details that are painful to rediscover by hand and are the real reason importing beats writing.

02 / Licensing

The map that decides everything

Licence bodies read, not SPDX badges trusted

GitHub reports most of these as "Other", which hides the clause that matters. Elastic License 2.0 says you "may not provide the software to third parties as a hosted or managed service". Actionist is precisely that. So the two biggest, best-designed catalogues in the space are study-only — not a grey area.

Trap 01

The MIT badge that buys nothing

Composio: 29,895 stars, MIT, "1000+ toolkits" in the description. The repo has no toolkit directory at all — ts/packages/ holds core, cli, providers, and nothing else. The MIT covers an SDK; the toolkits sit behind a paid hosted API.

Rule this gives us: an MIT badge says nothing about whether the valuable asset is in the repo. ls the directory before scoring a candidate.

Trap 02

The clause GitHub doesn't show

Nango and Airbyte both report SPDX NOASSERTION. Read the body and it is Elastic v2, forbidding hosted/managed service provision. Dify goes further — clause 1a: "you may not use the Dify source code to operate a multi-tenant environment."

Rule: read the LICENSE body for every NOASSERTION. Nango stays valuable as a schema teacher — best-designed provider format in the space — just never shipped.

04 / The blocker

No OSS gateway does multi-tenancy

Demonstrated, not inferred from schema

Two connections were created — github/tenant-a and github/tenant-b — then listed with a single admin token. All 23 connections came back in one flat list.

migrations/postgresql/0010_runtime.sql create table connections ( service text not null, connection_name text not null, value text not null, primary key (service, connection_name) ← no tenant column ); create table oauth_client_configs ( service text primary key ← ONE OAuth app per service, globally );

Two further findings from source: createSecretCodec silently returns a plaintext codec when the encryption key is unset, and keySalt is a hardcoded constant — so there is one global key, with no per-tenant derivation to configure. It does not exist.

Consequence: OpenConnector is a single-operator personal gateway; Actionist is a multi-tenant platform. Adopt the catalogue and the OAuth engine, write our own connection store. That layer was always going to be ours — this makes it explicit rather than a surprise in week three.
05 / The UI

The connect-account interface already exists, MIT, on our stack

Three keyword searches returned nothing; a directory listing found it

Activepieces ships the whole connect-account surface at packages/web/src/app/connections/ — MIT, and built on React + shadcn/ui + react-hook-form + i18next, which is our builder's own stack. It already covers the matrix we would otherwise discover the hard way.

Nango's SimplifiedJSONSchema is the pattern that removes per-connector frontend work entirely: 434 providers ship a constrained schema with field ordering, conditional visibility (visible_when), and per-value warnings — enough to render every connector's setup form from data, with no bespoke React per vendor. Read the shape; populate it ourselves.

06 / Build order

Cheapest real value first

Proposal — not started

One number inverts the obvious plan. API-key auth outnumbers OAuth roughly 2:1 in every catalogue independently — OpenConnector 1,302 vs 103; Activepieces 374 vs 96; Nango 323 vs 425. Three separately-built catalogues agreeing means it reflects the SaaS world, not one vendor's bias.

1 · Ship the API-key path

A form field and an encrypted write. No callback URLs, no per-vendor app registration, no refresh logic — and it unlocks ~90% of every catalogue.

2 · Import the catalogue over HTTP

cloud.activepieces.com/api/v1/pieces serves all 761 pieces as unauthenticated JSON with full auth specs. A ~20-line script, not the AST extractor originally scoped.

3 · Write the tenancy layer

Tenant column, per-tenant key derivation, mapping from Actionist users onto connection IDs. The real work item this research uncovered.

4 · Then OAuth2, one vendor at a time

Marquee connectors are disproportionately fiddly: 17 of Nango's 36 popular providers need custom scripts (47%) vs 9% catalogue-wide. The last twenty cost more than the first five hundred.

5 · Keep jentic as the long tail

CC0, so nothing to track. When a client needs an API the gateway lacks, the spec is almost certainly already among the 4,140.

Open before any client-facing UI ships: provider icon licensing is UNVERIFIED. OpenConnector's NOTICE disclaims trademark ownership; shipping Gmail/Stripe/Slack logos in a connector picker is a per-brand terms question. Cheap to check, embarrassing to discover late.
