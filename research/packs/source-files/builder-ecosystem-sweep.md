# Action Model / Client-Delivery Builder Ecosystem Sweep

Research date: 2026-08-26 (Asia/Ho_Chi_Minh)

Status: in progress. This report is being updated in three milestones: commercial product matrix, OSS/GitHub and adjacent infrastructure map, then shortlist and pilot stack.

## Scope and confidence

This is a coverage-led market and technology map, not an exhaustive enumeration of GitHub. It prioritizes first-party product documentation, pricing pages, trust/security pages, and canonical repositories. Commercial/private products are treated as product research; their hosted implementation is not assumed to be inspectable. OSS license labels are reported only when visible in the canonical repository or a primary project source. “Maturity” is a practical pilot-readiness judgment based on documented capabilities, release posture, and operational surface—not a vendor claim.

The target is an Action Model / client-delivery builder that can generate or modify real applications, operate previews or browsers, obtain approval, preserve rollback/evidence, and hand off portable code and infrastructure.

## Decision vocabulary

- **Reusable foundation** — safe to build the first pilot around (or a mature OSS primitive to embed).
- **Integration candidate** — useful external product/service to connect behind a stable adapter.
- **Pattern worth borrowing** — workflow or UX idea to reproduce without depending on the vendor.
- **Ignore / hold** — promising or adjacent, but currently too constrained, immature, or duplicative for the first pilot.

### Product-by-product implications

The commercial market has converged on a few distinct shapes rather than one universal builder:

1. **Prototype-to-host suites:** Lovable, Bolt, Replit, Base44 and Google AI Studio compress prompt→preview→publish and bundle some backend services. Their speed comes from managed state, but portability, external-repo import and evidence/approval depth vary sharply.
2. **Code/repo agents:** Cursor, Claude Code and GitHub Copilot keep Git and the customer’s environment as the source of truth. They are the strongest model for client handoff, branch/PR review and long-lived maintenance, but they do not solve domains, auth, data or hosting as one product.
3. **UI/design generators:** v0 and parts of Bolt optimize high-quality React/component output and design-system context. They complement a repo-first Action Model rather than replace its backend and governance plane.
4. **Vendor-native no-code:** Bubble and Retool have mature permissions, releases and hosting, but their native models make code portability and cross-vendor execution harder. They are valuable benchmarks for guardrails and enterprise controls, not obvious foundations.

### Commercial gaps an Action Model can own

- **Portable source-of-truth:** Keep a normal Git repository, declarative environment manifest and migration files first-class from the first prompt. Lovable’s current docs explicitly say existing GitHub repositories cannot be imported; Base44’s export is plan-gated; Bubble is vendor-native.
- **One approval contract across agents:** Build a risk-classified plan→diff→preview→test evidence→human approval→deploy state machine. Current products split this across Lovable drafts, Replit checkpoints, Cursor PR routing, GitHub rulesets and Retool releases.
- **Evidence as a durable artifact:** Save screenshots, console/network observations, test commands/results, environment digest, changed files, actor, model/tool calls and reviewer decision next to the run/PR. Browser testing is often useful but ephemeral or plan-gated.
- **Provider-neutral connectors:** Treat MCP/API connectors as scoped capabilities with explicit read/write and data egress policy. Vendor catalogs are useful but should not become the data model.
- **Safe environment promotion:** Test/staging/live with explicit data boundaries, migrations and backups. Lovable’s Test/Live is now closed to new Cloud projects; Replit snapshots and Retool environments show demand, but portable semantics remain a gap.
- **Client handoff and white-label:** Generate a delivery packet (repo, lockfile, env schema, migration history, deployment instructions, evidence bundle, ownership/access transfer) and make client-facing branding/domains independent of the builder. Most vendors gate branding, domains or export by plan.
- **Cost and scope control:** Use preflight estimates, per-run budgets, concurrency limits, approval checkpoints and visible tool/credit accounting. Several products meter tokens/credits while only some expose meaningful upfront estimates or spend controls.
