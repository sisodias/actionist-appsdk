# Action Model CRM / Revenue Operations research lane

**Research date:** 2026-08-26  
**Status:** active evidence programme; no candidate admitted; no build recommendation  
**Scope:** local SISO agency/client systems first, then a bounded primary-source GitHub/OSS sweep covering CRM, lead intake and enrichment, routing and follow-up, booking, renewals/engagement, call/email surfaces, automation, and auditability.

This report is a research artefact, not an architecture decision. A ranked candidate is a validation target, not a recommendation to build, fork, deploy, or purchase. Licence interpretation is engineering triage only and requires a proper legal review before distribution or hosted use.

- **Documented fact** — directly visible in a local source file, canonical upstream repository file, official API/deployment documentation, or GitHub metadata at the checked date.
- **Inference** — a bounded interpretation of those facts for the Action Model block contract.
- **Unknown** — not established by the sources read. Unknowns remain explicit; absence of evidence is not evidence of absence.

### 1.2 Local design evidence that should constrain later candidates

The existing SISOCRM research package supplies a useful contract rather than a candidate decision:

- [Repository-first research contract](file:///Users/shaansisodia/SISO_Workspace/SISO_Agency/apps/SISOCRM/research/campaigns/crm-github-debrief/REPO-FIRST-RESEARCH.md) requires a product/module dossier to cover product problem, screens, backend models/workflows/permissions/jobs/events/integrations, stack, exact licence, and a safe reuse lane. It distinguishes metadata-only, partial source read, and complete dossier.
- [Integration contract](file:///Users/shaansisodia/SISO_Workspace/SISO_Agency/apps/SISOCRM/integrations/contracts/README.md) makes route, identity, context, workflow, persistence, and recovery the minimum integration proof.
- [Canonical brokerage schema](file:///Users/shaansisodia/SISO_Workspace/SISO_Agency/apps/SISOCRM/db/001_brokerage_core.sql) separates party identity from buyer/listing relationships, preserves stage history, models access grants and expiry, and records audit events.
- [Capability blueprint](file:///Users/shaansisodia/SISO_Workspace/SISO_Agency/apps/SISOCRM/research/campaigns/crm-github-debrief/SISOCRM-CAPABILITY-BLUEPRINT.md) calls for typed events, bounded event-condition-action automation, layered permissions, saved-query reporting, and lead/opportunity → proposal/contract/invoice/payment lineage.

**Inference:** a usable RevOps block must preserve authority and replayable history across intake, communication, booking, opportunity, fulfilment, renewal, and reporting. A visually complete CRM that cannot expose idempotent events, ownership boundaries, or rollback evidence is not a safe foundation.

## 2. Reusable Action Model block contract

The local [block contract schema](file:///Users/shaansisodia/SISO_Workspace/SISO_Agency/clients/actionmodel/Actionist-AppSDK/SISO/design/block-contract.schema.json) requires an id, kind, provenance, stack contract, provided capabilities, and evaluation/admission evidence. For this lane, every serious candidate is mapped to the following additional fields before admission:

| Contract field | Minimum evidence required |
|---|---|
| `source` / provenance | Canonical upstream URL, checked commit/tag, root README, exact licence file, and all material subdirectory/edition boundaries. |
| `authority` | Named records for which the candidate is the system of record; explicit records it only projects or adapts. |
| `stack` / operational shape | Language/framework, database, queue/cache/object storage, external providers, deployment docs, upgrade path, and backup/restore story. |
| `data_model` | Primary entities, relationship keys, tenant/workspace keys, mutable versus immutable history, retention/deletion semantics, and migration path. |
| `api_events` | API surface, inbound/outbound webhooks/events, signatures, retries, idempotency keys, ordering assumptions, correlation/causation fields, and versioning. |
| `auth_tenant` | User/session mechanism, role/capability model, workspace/account/organization boundary, row/record isolation, SSO/OIDC behavior, and revocation. |
| `verification` | Unit/integration/e2e tests, fixture data, smoke command, route/identity/context/workflow/persistence/recovery evidence, and rollback drill. |
| `reuse_mode` | One of `whole-system-reference`, `contained-service`, `extractable-module`, `adapter-only`, `pattern-only`, `hold`, or `reject`. This is an engineering classification, not a legal opinion. |
| `risk_unknowns` | Exact claims not established by the source read; each unknown needs a bounded probe before admission. |

No block is admitted by this report. The existing project’s 389-record builder sweep and prior CRM campaign remain discovery inputs; they are not an exhaustive RevOps map and do not substitute for current candidate dossiers.

### 5.1 Twenty — extensible CRM/application platform

- **Classification:** foundation candidate; adapter-only or whole-system reference pending licence and integration proof.
- **Source/licence:** [README at the checked commit](https://github.com/twentyhq/twenty/blob/fcef2533c991c0ee33592b5a9b3f249bfa34b3e1/README.md), [root licence](https://github.com/twentyhq/twenty/blob/fcef2533c991c0ee33592b5a9b3f249bfa34b3e1/LICENSE), and [package manifest](https://github.com/twentyhq/twenty/blob/fcef2533c991c0ee33592b5a9b3f249bfa34b3e1/package.json) were read. The repository says most code is AGPLv3; files marked `@license Enterprise` are commercial; selected SDK/shared/UI/application packages are MIT. The licence contains a Twenty Application Exception for applications using the published APIs, webhooks, manifests, logic functions, front components, and SDKs without incorporating or modifying Twenty.

## 9. Smallest coherent evaluation slice and moat hypothesis

Because the research policy prohibits framing a near-term build recommendation as a conclusion, the following is an **evaluation slice**, not a proposed build stack:

```text
public intake / voice discovery
  -> canonical Lead + evidence + consent + audit
  -> dedupe/enrichment review
  -> assignment/routing decision
  -> Chatwoot conversation projection
  -> appointment adapter (Cal.diy or event-commerce adapter only if needed)
  -> Opportunity + stage history + next action
  -> bounded automation run / approval / retry log
  -> optional engagement touch (listmonk or Postiz)
  -> revenue/renewal projection only after ERP/payment authority is proven
```

The evaluation slice is intentionally one end-to-end correlation path, not a union of donor databases. The smallest useful proof should answer:

1. Can one external lead be captured exactly once, enriched with provenance, assigned, communicated with, booked, converted to an opportunity, and audited?
2. Can every donor event be correlated to the canonical lead/party/opportunity without making the donor and host both authoritative?
3. Can a failed provider, duplicate webhook, revoked user, or expired consent be replayed/recovered without silently changing revenue truth?
4. Can a renewal/payment event be projected later without rewriting the original opportunity or communication history?

**Moat hypothesis to test, not a conclusion:** the defensible advantage is more likely to be the Action Model’s authority-aware, event/correlation/retention contract plus vertical-specific operational evidence than a generic CRM screen or a broad AI workflow catalogue. This hypothesis is only defensible if the evaluation slice produces replayable receipts, clean source ownership, rollback/deletion proof, and reusable vertical schemas across at least two materially different client workflows.
