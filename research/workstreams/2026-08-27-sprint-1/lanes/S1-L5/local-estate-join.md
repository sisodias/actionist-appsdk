## 1. The single most valuable local asset for this lane

`SISOCRM/docs/DONOR_FORK_STANDARD.md` is the only artifact in the estate that describes a
**mixed-shape runtime and release cycle that has actually been operated**, rather than designed.
It is worth more to P14 than any vendor page, because it was written against a real donor (Teable,
AGPL-3.0 with Section 7 terms) that runs on its own process/origin inside a host shell.

What it establishes, verbatim-anchored:

| Mechanism | Observed rule | Which owned part it binds to |
|---|---|---|
| Pinned donor revision | Fork on a named branch, retain `upstream`, add as a **pinned Git submodule**; "The parent commit records the exact donor revision" | P14 ReleaseManifest — this is digest-equivalent pinning, already practised |
| Process/origin isolation | "Run the complete donor app on its own process/origin and mount it inside the host shell. Preserve its navigation, providers, state, and realtime behavior." | P14 runtime profile = `intact_service`/sidecar, not package-in-host |
| Anti-slicing rule | "Do not transplant a partial component tree unless the donor explicitly supports that embedding." | P13 — bounds what the editor may even offer for a donor surface |
| One writer per path | "One system owns each write path." Teable owns its editable physical table; a committed trigger projects into normalized CRM | P14 rollback scoping; matches A11 invariant |
| Host owns identity | Donor validates the HttpOnly host cookie server-to-server; "it never trusts browser-supplied user headers" | P14 preview isolation + P13 escape-hatch boundary |
| Rights as a release gate | "License notices and source-offer obligations are release gates." | P14 qualification — a gate that is legal, not technical |
| **Two-object rollback** | "Revert the parent commit to restore the previous pinned donor revision. **Data rollback is separate**: restore the pre-migration database dump" | P14 RollbackPlan — code and data are distinct objects |
| Standing UI rollback | Teable retains `/tables-native` as a temporary UI rollback while `/tables` is canonical | P14 — a *third* rollback object: surface-level fallback |

### Convergence finding (high confidence)

The commercial wave-1 census independently found that **artifact rollback ≠ composition rollback**
(Vercel reverts traffic but not env/config; Fly not `fly.toml`/secrets/migrations), and that
**a composition has two rollback horizons** (PlanetScale's ~30-min schema window vs unbounded
artifact rollback). SISOCRM's donor standard reached the same structural conclusion from operating
experience, and goes one further by naming a *third* object (a standing alternate UI surface).

Two independent derivations — one from vendor documentation, one from SISO's own operations —
converging on "rollback is not one object" is the strongest evidence this lane has produced.
It promotes the multi-object RollbackPlan from a design preference to a requirement.

The required-proof list in the same file is a directly reusable **P14 qualification checklist**,
and notably it is workflow-shaped rather than build-shaped: submodule resolves, donor health, SSR,
host-session login, logout revocation, realtime subscription, CRUD on records and fields, views/
filters/sorting/hidden fields "against real persisted data", backup-before-migration, persistence
after database restart, host+fork tests, and a human visual pass. This is exactly the P14 known
"a passing build is not client workflow proof", already instantiated.

## 2. AutoSaaS → P15 (the learning loop that exists on paper)

`apps/AutoSaaS/framework/autosaas-method.md` defines the factory loop ending
`launch kit → metrics and learnings → template registry improvements`, and §8 lists what each run
should update: template registry, source graph notes, **failed assumptions**, reusable prompt packs,
build wave patterns, verification scripts.

Two observations that constrain P15 honestly:

1. **The loop is procedural, not measured.** The document's own "Current Maturity" section records
   no machine-readable template registry, no built SaaS generated by AutoSaaS, no automated source-
   graph freshness check, no command runner. So the local precedent supplies *loop shape* and
   *update targets* — not evidence that such a loop improves outcomes. This matches ledger A37
   ("Production learning will improve retrieval and reuse decisions" — hypothesis).
2. **"Failed assumptions" as a first-class learning output is a genuinely good local idea** that the
   external census did not surface. Vendor learning loops rerank items; almost none record which
   *belief* was falsified. That maps onto P15's `Research priorities` output and is a candidate
   differentiator rather than a copy of prior art.

Also relevant: the five-area shell convention (§5) is an unproven archetype hypothesis (A15) — P13
must not assume the shell is fixed when defining what "reorder/replace" means at the shell level.

## 4. Universal Block Framework → P13 upgrade safety and P14 lifecycle

`phase-8/lanes/01-universal-block-framework/outputs/universal-block-framework.md` supplies:

- A **15-state lifecycle** with transition guards, and invariant 6 (revocation of a block propagates
  to every registry entry composing it → assemblies reopen to `held`). P14's release/rollback design
  must implement that propagation, and P15's demotion signal is what would trigger it.
- The **T0–T4 evidence ladder with an anti-averaging rule**: `evidence_tier` may never exceed the
  minimum tier across the nine families; "A single T1 family pins the whole block at T1 regardless
  of eight T4s." This is directly transplantable to P15 asset scoring — a shelf ranking that averages
  a fatal gap away is the same failure the ladder forbids. **P15 ranking must be min-gated, not
  weighted-averaged.** That is a first-principles constraint the external recommender census will
  not supply, because recommender systems are built to average.
- The **`deferred` fourth receipt status** (from `siso-ui-base/batteries/gates/principles-grep.mjs`,
  where a DNA-governed value "is reported as `deferred`, naming the DNA rule that overrides it, and
  does not fail the run"). P13 needs exactly this: an edit that violates a universal rule but is
  legitimately overridden by client-specific design authority is neither a pass nor a violation.
- Contradiction **X-3**: the forge/judge pipeline has **no numeric pass threshold** — `weightedOverall`
  computes a score, nothing compares it to a bar, and blessing is a human act. So the local visual
  gate is human-terminal. P14 must not claim automated visual gating; P13's "is this edit good?"
  question has no local automated answer either.

## 5. Composition architecture → P13 change plan and P14 staged writes

`phase-8/lanes/05-composition-agent-evals/outputs/composition-agent-architecture.md` supplies the
authority ladder `read < stage < write < message < deploy` and the staged-write protocol where
R5 emits diffs into `staging/<assembly_id>/`, receipts run, a deterministic policy gate gets a vote,
and *then* a named human decides — "A policy pass is not an approval; a human approval without
receipts is approval laundering." The approval event binds to the artifact hash, so approving
version A does not approve version B.

For P13 this is the ChangePlan execution model: a client's visual edit should produce a staged,
hash-bound, reviewable change — not a live mutation. It also supplies `ABSTAIN` as a first-class
output with the unsatisfied constraint named, which is the principled form of P13's open question
"How are unsupported requests explained?"

`HELD` is terminal until a named gate runs; it never decays to pass. K1–K7 kill rules apply.

## 6. Connector and corpus evidence → P15 caution

- OpenConnector generated **1,445 provider definitions and 15,156 actions** locally, but its global
  connection storage failed the required tenancy model (A26 rejected / A27 observed-at-spike-level).
  Lesson for P15: a catalogue's *size* is not a quality signal, and inheriting a catalogue can import
  an unsafe storage model. Reranking must score the reuse shape, not the catalogue.
- The 21st stores join to **8,515 unique identities**, of which **3,506 legacy entries are
  source-bearing** while much of the newer 7,949-entry harvest is bundle/metadata oriented. So the
  shelf P15 would rerank is mostly *not* source-bearing today.
- **A20/A21 remain unknown**: the ~1.3M-repository index and the 850k/80k Mini corpus have no
  authoritative path in current receipts. P15's refresh-schedule design must therefore be written
  against an *unknown-size, unknown-location* corpus and must not assume that feed exists.
- Phase-7/9 forensics: only **270 of 1,700** industry-repository pairs were complete at the measured
  baseline (1,430 deficit). Discovery breadth ≠ qualified supply. P15's cold-start priors cannot be
  seeded from corpus metadata alone.

## 7. What the local estate does NOT supply (honest gaps)

1. **No executed runtime, deployment, or rollback receipt anywhere.** `execution_status=UNEXECUTED`,
   `admitted_blocks=0` across every phase artifact. SISOCRM's donor standard describes practice but
   this lane read a *standard*, not a run log — it is `[direct]` evidence of the documented rule,
   `[inferred]` evidence of operational reality.
2. **No production learning data at all.** Zero accepted plans, zero recorded client edits, zero
   incidents, zero maintenance outcomes. P15 must be designed for the cold-start case because the
   cold-start case is the only case that currently exists.
3. **No editor.** There is no local bounded-edit implementation to study; the closest is the
   `brief → forge → gate → judge → bless → graduate` loop, which is a *generation* pipeline with a
   human terminal, not a client-facing editor.
4. **No numeric quality threshold** anywhere in the local pipeline (X-3).
5. **No measured adaptation cost** — A07 ("adaptation is always only 1–2% of the work") is `unknown`,
   and P15's headline ranking input (observed adaptation cost) therefore has no baseline distribution.
