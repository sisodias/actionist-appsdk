# Phase 8 synthesis — the Universal Block Foundry

Observed: 2026-08-27  
Research status: **five lanes independently verified; unpromoted**  
Product status: **UNEXECUTED / NOT_ADMITTED / admitted blocks 0**  
Parent objective: **active and materially incomplete**

## Executive decision

The research converges on a sharper product than “recreate Lovable.” Actionist should become a governed **Universal Block Foundry**:

```text
source identity
  → rights/provenance disposition
  → source-shape decision
  → dependency and boundary closure
  → typed block contract
  → evidence receipts across nine orthogonal families
  → scoped registry admission
  → deterministic compatibility elimination
  → bounded agent planning and glue
  → human-authorized release and rollback
```

The useful unit is not a repository, a generated page, or a component screenshot. It is a versioned block whose identity, delivery mode, interfaces, dependencies, data/tenancy boundary, visual/token contract, runtime, maintenance, economics, recovery, rights and authority are explicit enough to be rejected mechanically when evidence is missing.

This phase does **not** prove the foundry works. It provides a coherent contract and falsifiable pipeline. No block is admitted and the first composition pilot remains blocked.

## What each lane contributed

### 1. Universal Block Framework

Lane 01 joined Block Contract v1, design v0, AutoSaaS, `siso-ui-base`, SISOCRM donor practice, Great Library and the 17-industry taxonomy. Its proposed delta contains:

- eight contract additions;
- nine orthogonal evidence families;
- 15 lifecycle states and 14 transitions;
- ten fail-closed invariants;
- seven cross-system contradictions;
- eight falsifiers;
- two blocking defects in the current contract.

The major additions are `packaging_mode`, composition join semantics, registry/admission scope, reference-only use controls, mechanical evidence tiers and restored stack compatibility. The two immediate defects are load-bearing:

1. Block Contract v1 hardcodes major version `1` in its identifier regex, so a v2 block cannot validate.
2. The v0 `requires` dependency edge disappeared in v1, leaving no representable graph for composition.

### 2. Local Corpus Join

Lane 02 proved that the laptop has two complementary 21st-derived stores:

| Store | Population | Primary artifact |
|---|---:|---|
| New `siso-ui-base` harvest | 7,949 | compiled bundle, preview, demo and metadata |
| Legacy design-system store | 3,508 | source-bearing `.tsx` for 3,506 entries |
| Intersection | 2,942 | both artifact shapes |
| Joined union | 8,515 | unique upstream identities |

The headline corpus size is not eligible block supply. Only two license fields were found across 11,549 third-party records. The current first-party 21st.dev terms prohibit unconsented scraping, AI-training use, and reuse/republication of structured metadata or media. The stores remain valuable for research, visual precedent and source discovery, but admission requires per-item provenance, license and counsel gates.

The lane also confirmed AutoSaaS and Great Library as process/provenance substrates and exposed stale estate paths. The claimed Mini 850k/80k corpus remains unresolved because no exact current path or owner manifest was established.

### 3. B2B Template Shelf

Lane 03 created the missing app-level layer between components and industries:

- ten archetype identifiers;
- a 20-required-field template contract;
- 17 pinned source records;
- 34 unique industry-archetype pairs across the 17-industry denominator;
- four candidate, eight reference and five hold dispositions.

The central result is a supply/demand inversion. `case_workflow` is primary for six industries and `portal` is secondary for six, yet these highest-demand archetypes have the thinnest clean-license supply. Generic CRM, admin and dashboard starters are abundant but weakly differentiated. `marketplace` has no demand anchor and should not be built speculatively.

The first shelf should therefore be designed around reusable domain skeletons rather than copied app templates: case/workflow, client portal, finance operations, inventory, scheduling, support, field operations, learning/content and CRM. Industry variants should change domain entities, authority, obligations and workflows while reusing shared atoms and governed infrastructure.

### 4. Repo-to-Block Mechanics

Lane 04 defined 11 pipeline stages, of which ten are conversion stages before/including admission, four source shapes, 23 negative paths and four worked traces. Its 18-row mechanism census classifies eight mechanisms as deterministic, four as deterministic but environment-bound, and six as semi-deterministic.

It preserved all 14 Block Contract v1 receipt types and all 14 inherited required fields, then proposed three missing receipt types:

- `source_identity` at Stage 0;
- `shape_decision` at Stage 2;
- `dependency_closure` at Stage 3.

The most important ordering correction is that **identity precedes rights**. Phase-7 rights work often lacked immutable commits and digests. Rights findings against an unpinned moving repository do not create a reusable source identity.

The lane also establishes that full automation is the wrong target. Shape choice, semantic adaptation and admission require named human accountability. Deterministic tools can compute evidence and constrain choices; they cannot decide business equivalence, legal permission or client authority.

### 5. Composition Agent and Evals

Lane 05 selected S2 `plan-then-fill` over a monolithic composer and negotiated multi-agent strategy. Its key architecture choice is a **model-free deterministic solver** between retrieval and model choice:

```text
interpret demand → retrieve candidates → eliminate incompatible sets deterministically
→ model chooses among verified feasible sets → bind/glue → staged verification
```

The evaluation suite contains 26 fixtures, eight positive and 18 negative, with three held-out and three zero-tolerance cases. It defines eight axes, six tiers, seven kill rules and ten compatibility constraints.

This preserves the cheap-model thesis honestly: models do bounded interpretation and choice, while deterministic logic owns compatibility, authority, scope, namespace, rights and tenancy rejection. `UNDERDETERMINED` is a valuable output because it identifies a missing contract field instead of hiding uncertainty behind model confidence.

## Cross-lane dependency result

Three composition dependencies are now resolved at design level:

- DEP-05: lane 04 receipt schema and hashing structure;
- DEP-06: lane 03 archetype identifiers and variants;
- DEP-07: lane 02 verified local inventory, with rights gates retained.

Three fields required for even the model-free Stage-0 composition dry-run remain unresolved:

1. `action_contract.capabilities` enum;
2. an explicit `admitted_for_host_scope` field—the lane-01 `registry.admission_scope` proposal may be equivalent, but the name and semantics are not joined;
3. a canonical `license_state` enum with quarantine semantics.

End-to-end execution additionally requires at least one admitted block, an Actionist host/auth/data/deploy contract, a client outcome-fit rubric and explicit authorization for model/sandbox execution. None exists today.

## Framework assembled from the evidence

### Block identity

Every candidate begins with a canonical source URL, immutable revision, declared digest domain and content digest. Repository search records without these fields remain discoveries, not conversion candidates.

### Packaging mode

The contract must distinguish:

- intact fork;
- intact service/runtime;
- extracted slice;
- generated from pattern;
- reference-only.

This distinction is necessary to represent SISOCRM's intact donor practice without pretending that running an intact upstream service is equivalent to copying an extracted block.

### Nine evidence families

Evidence remains orthogonal and fail-closed:

1. identity/versioning;
2. provenance/rights;
3. dependency closure;
4. interface contract;
5. data/tenancy;
6. visual/token contract;
7. runtime/sandbox;
8. maintenance/economics;
9. rollback/owner/authority.

The block tier is the minimum tier across all nine families. Strong visual evidence cannot compensate for unknown rights; a clean license cannot compensate for unknown tenancy; a passing build cannot compensate for missing rollback ownership.

### Demand graph and templates

The 17 industries should not create 17 duplicated stacks. Demand collapses into approximately ten archetypes over 12 atoms. Templates are governed compositions of blocks plus industry deltas—not giant copied repositories.

### Composition

Retrieval proposes candidates. The compatibility solver removes anything not admitted for the host scope, rights-incompatible, port-incompatible, tenant-incompatible, namespace-conflicting or outside authority. The model receives only feasible sets and bounded choices.

### Human authority

Human judgment is not an embarrassment to automate away. Named reviewers own shape choice, semantic adaptation, rights/legal review, data authority and admission. Silence is not approval, and a model cannot grant itself broader authority.

## Eight contradictions that remain visible

1. **Large local corpus versus reusable supply:** 8,515 identities, but only 2/11,549 license fields and restrictive current marketplace terms.
2. **17,000 observations versus 1,700 complete repositories:** only 270 industry-repository pairs cover all ten dimensions.
3. **Composition design versus zero admitted blocks:** architecture is research-complete; no end-to-end run is possible.
4. **Automated conversion versus semantic responsibility:** eight DET, four DET-ENV and six SEMI mechanisms; human authority remains at key stages.
5. **Template abundance versus demand:** commodity boilerplates are saturated while case/workflow and portal supply is thin.
6. **v2 framework versus v1 identity:** the current regex rejects every proposed 2.x identifier.
7. **Intact AGPL donor operations versus reference-only harvest policy:** packaging mode clarifies the technical distinction; legal confirmation remains absent.
8. **Research maturity versus client readiness:** runtime, security, economics, client/legal and admission receipts are still unexecuted.

## Correct next experiment

The next experiment should not be another broad repository wave. It should be a model-free, execution-free contract sufficiency dry-run over synthetic records:

1. adopt or revise the three missing composition fields;
2. create one synthetic block record per source shape;
3. emit Stage 0 identity, Stage 2 shape and Stage 3 dependency receipts using lane 04's schema;
4. run the lane-05 deterministic solver over positive and negative fixtures;
5. record every `UNDERDETERMINED` result as a contract defect;
6. perform no build, model call, sandbox action or admission.

Only after the contract survives this dry-run should an authorized clean-room pilot select one permissively licensed source, perform rights/SBOM/security/runtime/economics gates and attempt a single scoped admission.

## Completion boundary

This synthesis is therefore a directional framework and falsifiable research result, not a production architecture approval.

## External connector input

The completed connector lane materially narrows the integration strategy. Its final report counted 1,445 OpenConnector provider definitions, 761 Activepieces pieces and 982 Nango providers. It recommends reusing OpenConnector's catalogue and OAuth-engine patterns while owning the Actionist connection store and tenancy boundary.

The useful correction is that catalogue size does not equal implementation uniformity. Nango's long tail is mostly declarative—895 of 982 providers—but 17 of its 36 `popular` providers are scripted. The connectors clients ask for first are therefore disproportionately expensive. Activepieces' public catalogue API avoids a bespoke AST extractor, and Nango's constrained setup schemas demonstrate a path to generated credential forms.

The execution spike strengthened this result. OpenConnector generated 1,445 providers and 15,156 actions locally, executed both unauthenticated and authenticated actions, encrypted credentials at rest, rejected an invalid token before persistence and generated a valid Google OAuth authorization URL. It also proved the tenancy blocker: one admin token lists all named connections, OAuth client configuration is global per service and there is no per-tenant key derivation. This supports the catalogue-and-OAuth-engine adoption seam while falsifying adoption of the storage layer.

This input does not alter Phase 8's admission boundary. Provider-icon rights, tenant ownership, production secret storage and connector admission remain open.
