## Brief reconstructed from the project record

The original ask combines several distinct jobs:

1. Map platforms that can turn prompts, designs, data, or repositories into
   applications or workflows, including Lovable-like builders, coding agents,
   visual builders, workflow systems, browser agents, sandboxes, and private or
   open-source alternatives.
2. Deep-dive capabilities, pricing/usage, API and MCP surfaces, import/export,
   deployment, tenancy, authority, audit, portability, maintenance, support,
   rollback, lifecycle, and vendor continuity for each relevant platform.
3. Find useful open-source building material across GitHub, preserving query,
   source-path, license, activity, capability, vertical, and disposition
   evidence instead of copying or automatically admitting repositories.
4. Repeat the discovery and comparison by the 17 target industries, joining
   industry demand to atoms, blocks, standards, and exact evidence cells.
5. Work from first principles: maximize client value per token and time by
   assembling bounded, governed, reusable units rather than recreating a
   prompt-to-screen demo.
6. Make the result viewable as a local HTML research room with direct links to
   the underlying packets and machine-checkable state.

The record does not establish that the local 21st.dev/UI hub, the full private
builder universe, an AutoSAS corpus, or a million-repository indexed archive
has been located and joined. Those are open discovery requirements, not facts
to infer from the 500-row GitHub tranche.

## What the data says

### The crowded layer is generation

Prompt-to-screen, visual editing, hosted publishing, coding agents, workflow
graphs, and browser automation are all represented by multiple surfaces. A
new generator alone is unlikely to be the durable Action Model advantage.

### The scarce layer is governed last-mile delivery

Across the company, public, standards, and GitHub evidence, the repeated
unresolved surfaces are auth and authority, data ownership and correction,
integration/version drift, tenancy, security, portability, bounded cost,
observability, maintenance ownership, and rollback. The product opportunity is
an evidence-bearing assembly and operations layer around those boundaries.

### The reusable unit is an atom plus a contract

A repository is a source candidate. An Actionist block must additionally name
its inputs, outputs, data entities, UI states, action ports, authority scope,
source and rights, verification fixture, audit receipt, owner, deployment
boundary, maintenance plan, and recovery/rollback behavior.

### The safest first pilot is read-only

The operations/read-model archetype offers useful value while limiting
external side effects. Finance, CRM/lead, and support remain attractive but
need stronger authority, legal, data, message, and SLA gates before writes or
outbound actions.

## Admission gate contract

An observed repository, vendor feature, or public signal cannot enter the
reusable-block catalogue solely because it has stars, a working demo, a
permissive-looking license, a pricing page, or a compelling case study.

| Gate | Required receipt | Current state |
|---|---|---|
| G1 — canonical contract | Versioned Block Contract with ports, state transitions, ownership, authority, errors, idempotency, audit, and recovery | **Missing** |
| G2 — provenance and rights | Pinned source identity, dependency/SBOM output, SPDX/REUSE/OpenChain treatment, obligations, provenance, and correction/exit path | **Design exists; scan absent** |
| G3 — capability and model eval | Synthetic fixtures, expected outputs, negative cases, model/version/cost record, threshold, and reproducible receipt; include the 20-task cheap-model hypothesis | **Design exists; eval absent** |
| G4 — authority and security | Least privilege, audience/sender binding, expiry, consent, revocation, secret handling, isolation, denial, and abuse/egress probes | **Design exists; probes absent** |
| G5 — runtime and portability | Pinned environment, build/runtime proof, data/auth/schema/job/asset export, deploy receipt, health, restore, and rollback/compensation proof | **Unexecuted** |
| G6 — economics and maintenance | Denominated accepted outcome, token/compute/browser/API cost, repair rounds, support owner, freshness, drift, and exit cost | **Unknown** |
| G7 — client/legal boundary | Client-owned data/authority assumptions, consent/retention, regulated-domain review, contract/SLA, and explicit implementation approval | **Missing** |

Admission rule: a block remains `not_admitted` if any gate is missing,
unverifiable, or contradicted. A public source or repository observation may
motivate a probe; it cannot substitute for the receipt.

## Next bounded work packages

1. **Freeze the canonical Block Contract.** Turn the first-principles decision
   into a versioned local schema with JSON fixtures, lifecycle states, denial
   paths, audit fields, and evidence IDs. This is the highest-leverage missing
   input because every later scan, eval, and platform comparison depends on it.
2. **Run a synthetic read-only benchmark.** Use operations, finance, CRM/lead,
   and support fixtures with pre-registered pass/kill criteria. Compare model
   routes and repair rounds, including the cheap MiniMax hypothesis, without
   client data or external side effects.
3. **Prioritize clean-room platform and repository probes.** Select a small
   evidence-backed set from the 67 surfaces and 500 discovery records. Test
   export, auth/data boundaries, source rights, build, runtime, visual states,
   cost, and recovery before considering a block candidate.
4. **Locate the missing local corpora.** Inventory the UI hub, any 21st.dev
   component store, AutoSAS material, private-builder archives, and larger
   GitHub index. Record paths, ownership, license, freshness, and dedupe
   results as separate packets.
