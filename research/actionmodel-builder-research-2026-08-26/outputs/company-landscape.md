## Executive summary

The reviewed market is not one homogeneous “AI app builder” category. It is a set of overlapping product shapes:

- prompt-to-app suites compress intent, code, backend, preview, and publish into one hosted lifecycle;
- repo-native coding agents preserve Git and customer environments but usually do not provide a complete app runtime;
- data-native internal-tool builders make schema, permissions, environments, and audit more explicit but are less portable;
- design-to-code products cover visual-to-frontend handoff rather than data, authorization, or rollback;
- browser/computer-use products operate existing software but do not automatically provide authority, idempotency, recovery, or evidence contracts;
- workflow builders supply typed tools, approval steps, and execution history, but are not reusable client-app builders; and
- sandbox vendors provide execution primitives, not a complete governed build plane.

The strongest repeated market pattern is:

```text
intent → project/repository/data context → generated or assembled change
→ preview/test → publish or PR → partial history, permissions, and usage
```

The most important unresolved boundary is:

```text
provenance and license admission → typed block contract → safe data/auth ports
→ isolated execution → independent verification and deployment proof
→ approval before external side effects → durable evidence and rollback
```

That boundary is a strategic inference (`I`), not an authenticated Actionist capability and not a claim that every incumbent lacks it. No live vendor session, paid account, API call, generated application, or deployment was used in this lane. The matrix therefore records first-party documentation (`D`) and direct source inspection (`E`), while retaining unknowns (`U`) instead of promoting marketing language to proof.

## Evidence and inclusion rules

Evidence classes follow `PROGRAM.md`:

- `E` — a first-party product, documentation, pricing, API, or repository artifact was directly inspected.
- `D` — the source documents the claim; it is not independently authenticated by a live run.
- `I` — an inference from multiple evidence points or a recommendation.
- `U` — unknown or not established in the reviewed source set.

Every matrix row includes an observation date, evidence class, confidence, capability tags, commercial boundary, disposition, open question, and direct first-party source links. “Commercial/private company” includes a private vendor, a public-company product group, or a commercial product with an open-source adjacent runtime. Browserbase and Stagehand are consolidated into one company row. Google AI Studio, Firebase Studio, and Antigravity are consolidated into one Google row. This prevents product-family duplication while preserving distinct inspected surfaces.

The following claims are intentionally *not* treated as proof of stronger capabilities:

- a preview or publish button is not proof of production deployment;
- version history, Git sync, checkpoints, or a revert button is not proof of complete code, database, credential, deployment, and external-side-effect rollback;
- an API, MCP server, connector catalog, or marketplace is not proof of OEM, white-label, tenant isolation, or procurement rights;
- a repository license is not clearance for its dependencies, assets, generated artifacts, or the hosted service; and
- a documented browser agent is not proof of typed authority, approval, idempotency, post-action verification, or recovery.

## Findings for Action Model

1. **Generic prompt-to-app is a crowded benchmark surface, not a differentiated contract.** Lovable, v0, Bolt, Replit, Base44, Manus, Bubble, and Google all document meaningful portions of the intent-to-preview/publish path. This is a market observation, not a quality leaderboard.
2. **Repo-native agents are the cleanest handoff pattern.** Cursor, Claude Code web, GitHub Copilot cloud agent, and Replit preserve branches, PRs, permissions, environment setup, or test execution more explicitly than vendor-native app builders. They still leave data, auth, hosting, and client deployment to the surrounding system.
3. **Data-native builders make authority more visible.** Airtable, Retool, ToolJet, NocoBase, Appsmith, and Bubble expose permissions, schemas, environments, plugins, or recovery patterns. Their runtime models are often vendor-shaped and therefore not automatically portable.
4. **Design-to-code stops before the hard contract.** Builder.io, Visily, Uizard, Locofy, Onlook, v0, and Bolt prove demand for visual/frontend generation. The reviewed evidence does not prove raster-to-token IR, human token approval, fixed registry IDs, backend ownership, or visual regression as one chain.
5. **Browser operation is an adjacent plane.** Browserbase/Stagehand and Skyvern provide credible substrate patterns; Cursor and Google add agent/browser artifacts. The Actionist opportunity, if validated, would be the authority/evidence/recovery contract around an operation, not browser control alone.
6. **Sandboxing is rentable; admission is not solved by renting.** Modal, Daytona, and E2B expose useful isolation/runtime choices. The next evidence gate is a small cost/security/tenant/network/cleanup comparison, not another broad vendor list.
7. **The next defensible research unit is execution-class evidence.** The matrix does not authorize implementation. A bounded future proof should test one source-cleared scaffold or block through provenance, adaptation, isolated build, browser smoke, visual evidence, deployment distinction, owner, and rollback receipts.
