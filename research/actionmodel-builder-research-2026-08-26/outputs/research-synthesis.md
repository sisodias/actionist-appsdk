## Executive decision

The research phase is complete enough to make the strategic decision:

> Action Model should not begin as another unconstrained Lovable clone. The defensible hypothesis is a governed assembly and operations layer around a known client data/deployment boundary.

The market already compresses:

```text
intent → generated code → preview → publish
```

The proposed Action Model seam is the harder loop:

```text
client outcome
→ solution atom
→ candidate source discovery
→ provenance/license admission
→ Block Contract
→ bounded adaptation
→ data/auth/token grounding
→ isolated execution
→ independent verification
→ human authority
→ deployment and operation
→ audit, recovery, and rollback
```

This is a strategic inference, not a proven product capability. No repository is
admitted, no Actionist runtime contract is authenticated, and no client build is
authorized by this packet.

## What the data establishes

### 1. The generic build plane is crowded

The 31-company matrix covers prompt-to-app builders, repo-native coding agents,
data-native internal-tool platforms, design-to-code tools, browser/computer-use
systems, workflow/agent orchestration, and sandbox runtimes. The repeated market
pattern is intent, context, generation or assembly, preview, and some form of
publish/history/usage control.

The strategic conclusion is not that every vendor is equivalent or that any
vendor is best. It is that generic generation is a crowded comparison surface.
The differentiated question is what happens after the first plausible screen or
scaffold exists.

### 2. The last mile is the repeated failure boundary

The public-signal lane found real bounded apps and workflows being shipped, but
the repeated friction clusters at:

- stateful integrations and authentication;
- data migration, tenancy, permissions, and environment separation;
- regressions caused by broad regeneration;
- opaque credit/token burn during repair loops;
- incomplete portability of data, secrets, storage, and deployment state;
- rollback that covers files but not databases or external side effects; and
- security, audit, and production-hardening work.

These signals are useful demand and failure evidence, not an adoption denominator
or an independently audited quality benchmark.

### 3. The corpus is large enough for discovery but not admission

The new GitHub corpus contains 284 unique repositories across nine lanes:

| Lane | Records |
|---|---:|

| scaffold | 38 |
| registry | 32 |
| AST/codemod | 32 |

The final JSONL passes jq and Python validation, has 284 unique repositories,
and records the GitHub search-rate limitation. Browser/eval/provenance rows were
added through explicit first-party seed records plus repository API, README, and
top-level contents inspection when search results were rate-limited. That is
honest content evidence, but it is not an exhaustive search claim.

The dispositions are:

- 156 candidate leads;
- 15 reference-only records;
- 108 holds;
- 4 rejects; and
- 1 explicit unknown.

The word “candidate” means relevant enough for a separate pinned-source,
license, adaptation, contract, build, and recovery gate. It does not mean safe,
portable, legally clear, or admitted.

### 4. Standards form an evidence stack, not a magic trust badge

The standards lane mapped the useful parts of SPDX/REUSE/OpenChain, SBOM and
provenance systems, SLSA/in-toto/OCI/SCITT, AST and codemod tooling, DTCG and
registries, OpenAPI/JSON Schema/Pact/AsyncAPI/CloudEvents, MCP/OAuth/policy,
evaluation suites, sandboxing, tenancy, deployment, and rollback.

The important boundary is compositional:

```text
rights/provenance receipt
+ source and host contract
+ data/auth/action contract
+ build/contract/browser/visual proof
+ authority and recovery receipt
```

No individual standard proves the whole statement “this source became this safe
client behavior.” That relationship must be maintained by a local evidence graph.

### 5. The atomic unit is a solution atom, not an industry or repository

The first-principles lane defines a solution atom as:

```text
outcome + trigger + source state + observation + decision + side effect
  + authority/approval + verification + recovery + audit evidence
```

The reusable software unit is a **Block Contract**: a versioned artifact with
pinned provenance, license/dependency evidence, host/data/UI/action ports,
adaptation history, machine-readable proof, an owner, and a rollback boundary.

An industry is a prioritization and vocabulary layer. A repository is a source
candidate. Neither is the unit that can safely be composed or released.

## The next work, in order

### Gate 1 — Freeze broad discovery and normalize the evidence

Create one claim ledger across the company, GitHub, standards, and public-signal
packets. Each row should carry source URL/path, observed date, evidence class,
confidence, capability, limitation, and decision impact. Reconcile the earlier
commercial matrices instead of quoting them as separate totals.

Do not expand the company or repository lists until a specific gap in this ledger
requires it.

### Gate 2 — Build the niche → atom → block join

For each provisional pilot, map:

```text
industry/use case
→ solution atom
→ required capabilities
→ candidate block or vendor primitive
→ adaptation and contract burden
→ evidence status
→ missing gate
```

This is the most important missing analysis. The vertical catalogue and the OSS
corpus exist, but the join between demand and reusable capability is not yet
proven.

### Gate 3 — Obtain the Actionist canonical contract

Research cannot infer the private product boundary. Before implementation, record
the first-party answers for:

- canonical API/SDK and authentication;
- data ownership, tenant key, RLS, and allowed write modes;
- deployment, domains, environments, and secrets;
- approval, audit, idempotency, and external side effects;
- design-token/component registry expectations; and
- rollback/compensation boundaries.

If these cannot be stated, the pilot remains a framework exercise rather than an
Actionist build.

### Gate 4 — Test the cheap-model hypothesis

Use one fixed scaffold, one fixed block set, synthetic fixtures, and 20 bounded
tasks. Pre-register requirement coverage, build/contract pass, repair rounds,
tokens, wall time, evidence completeness, and escalation rate.

The question is not “can the model generate code?” It is:

> Can a cheap model make a bounded, machine-verifiable change inside a known host without destroying existing contracts?

If it fails, the architecture must narrow the task class, use a stronger model,
or abandon the assembly assumption before corpus-conversion work scales.

### Gate 5 — Admit one candidate end to end

Select one permissively declared, low-sensitivity candidate from the held corpus
and run the complete ladder:

1. immutable source and pinned commit;
2. file/dependency/asset license and SBOM scan;
3. extraction boundary and adaptation log;
4. Block Contract instance and provider/consumer checks;
5. isolated build with explicit network and secret policy;
6. contract/browser/visual proof appropriate to the block;
7. named owner and deployment distinction;
8. separate code, database, deployment, and external-side-effect recovery plan;
9. human admission decision.

Until this exists, “reusable block library” is a discovery programme, not a
working system.

### Gate 6 — Model economics and threats

Measure cost per successful outcome rather than cost per attempt. Include model
tokens, context packaging, failed repairs, sandbox time, human review,
maintenance, license/legal risk, and hosting.

Threat probes should cover repository prompt injection, poisoned tool metadata,
secret egress, malicious dependencies, license laundering, cross-tenant access,
and irreversible external actions. A green build is not a security receipt.

## Decision tree after the gates

```text
cheap-model benchmark + one admitted block + Actionist contract pass
├── yes → build one narrow governed operations pilot
├── partial → use a hybrid (buy/build execution or generation primitives,
│            keep Actionist provenance/authority/evidence as the control plane)
└── no → change scope or architecture; do not build a general Lovable clone
```

## What must not be claimed yet

- The 284 GitHub records are not 284 reusable blocks.
- The 156 candidate dispositions are not legal or technical admissions.
- The public signals do not establish retention, market share, or a random
  production-success rate.
- The industry catalogue does not prove authenticated Actionist capability.
- The standards map does not prove semantic equivalence, safe tenancy, or legal
  clearance.
- The local 850k/80k corpus scale remains unverified and should stay quarantined
  from external material until the Mini data plane is inventoried.
- No implementation, deployment, API integration, or client data handling is
  authorized by this research run.
