# Luna competitor and feature-census findings

Lane: competitor/platform feature census
Researcher: Luna explorer B / Noether
Status: local evidence review complete; census expansion and taxonomy reconciliation pending
Boundary: no private access, login, paid account, API key, runtime execution, generated app, deployment, source modification, or admission.

## Baseline finding

The authoritative platform register contains 117 normalized product surfaces: 67 existing records and 50 expansion candidates. Phase-4 through Phase-6 packets deepen ranked slices but do not create one normalized evidence row for every competitor × feature combination.

The current register is therefore a strong indexed foundation, not an exhaustive census.

The product surface must be the census unit. Company identity, product family, aliases, rebrands, successors, OSS siblings, dependencies, and lifecycle events must be separate edges. This avoids conflating products such as Bolt.new and bolt.diy, or Google AI Studio, Firebase Studio, and Antigravity.

## Declared inclusion protocol

A product surface enters the declared universe when it satisfies at least one inclusion test:

1. It turns natural-language, visual, repository, data, or workflow input into an application, interface, code change, automation, or agent.
2. It supplies a material runtime primitive: data/auth, execution sandbox, browser operation, deployment, orchestration, or durable recovery.
3. It is a direct substitute for a builder workflow used by a non-technical or semi-technical team.
4. It is a control plane, registry, SDK, or infrastructure product that can capture part of the builder value chain.
5. It appears in at least two independent discovery lanes.

The universe must be exhaustive against this declared protocol, not an unbounded claim about every company on the internet.

This is a count contradiction, not a cosmetic discrepancy:

- stated count: 68;

- accepted count for this artifact: none yet;
- status: taxonomy_count_conflict;

## Feature-row evidence contract

The unit of evidence is one product surface × feature key row. Every row must separate product claim from capability proof and retain:

- competitor, surface, and company identities;
- feature domain, stable key, and taxonomy version;
- status: observed, partially_observed, not_found, gated, contradicted, legacy, shutdown, unknown, or not_applicable;
- evidence class: E/D, E/U, V, X, I, or U;
- first-party claim text and source URL;
- source kind, observation date, publication date, HTTP/access state;
- capability-proof status, method, fixture, and result when independently tested;
- limitations and explicit unknowns;
- falsifier and next read-only gate;
- lifecycle, rights, provenance, and research-only boundary.

A search-result snippet, star count, generic description, or capability tag cannot serve as sole feature evidence.

The distinction between not_found and unknown must be retained:

- not_found means a declared bounded search found no claim;
- unknown means the source was inaccessible, thin, ambiguous, or not searched sufficiently.

## Highest-value missing rows

Prioritize rows that distinguish a hosted demo from a durable, governable, client-owned builder:

1. Complete exit object: source export, backend export, auth export, history export, and independent rebuildability.
2. Rollback scope: source, schema, data, secrets, deployment, external side effects, replay/idempotency, and recovery receipt.
3. Authority and consent: agent identity, per-tool scope, enforceable approval, postcondition checks, and durable execution receipts.
4. Tenant/security boundary: tenant isolation, network controls, secret isolation, sandbox boundary, residency, admin controls, and incident response.
5. Mobile production path: mobile distribution, store gates, mobile rollback, source/backend export, especially for FlutterFlow, Draftbit, Adalo, Thunkable, Bravo Studio, Bubble, Replit, and Anything.
6. Design fidelity and provenance: tokens, visual validation, asset ownership, component identity, and input-to-output lineage.
7. Economics of a successful build: usage unit, model cost, runtime cost, spending controls, export cost, and cost per accepted build.

These are product comparison rows, not runtime capability claims. Authenticated behavior, live behavior, rights clearance, and client economics remain unknown unless a later authorized receipt proves them.

## Bottom line

The 117-record platform register is useful but not exhaustive. Phase 7 should first declare the product-surface universe, reconcile the 68-versus-144 taxonomy count, add the missing mobile and adjacent runtime clusters, and then populate one evidence row per surface × feature with explicit unknowns. The feature census must not be promoted until its universe, key count, row count, dedupe edges, source dates, and unresolved states are machine-verified.
