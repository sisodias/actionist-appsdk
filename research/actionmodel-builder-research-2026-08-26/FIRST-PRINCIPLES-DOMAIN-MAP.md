# Actionist Builder — first-principles domain map

Date: 2026-08-27  
Status: architecture decomposition for discussion; not an implementation approval  
Scope: the system that turns demand plus reusable internet/local software into maintainable, semi-custom client applications.

## 1. Start from the outcome, not the inherited framework

The desired outcome is:

> Given a bounded client outcome, produce the highest-value working application quickly, cheaply and repeatably by reusing proven capabilities wherever possible.

That outcome does **not** imply that every repository becomes one kind of block, every block uses one database, or every application is generated by one agent. Those are candidate implementation choices.

The irreducible jobs are:

1. Understand the client outcome.
2. Describe the required product without prematurely choosing code.
3. Find relevant capabilities, patterns and complete systems.
4. Decide the correct reuse shape for each capability.
5. make heterogeneous capabilities interoperable at explicit seams.
6. Compose a coherent product rather than a bag of features.
7. Prove the product works as a system.
8. Operate, change and repair it over time.
9. Learn from each build so the next one is cheaper and better.

This decomposes into five planes and eighteen owned domains.

## 2. The five planes

```text
Demand plane
  outcome model -> industry model -> product specification

Supply plane
  source intelligence -> capability mining -> source-shape decision
  -> extraction/adaptation -> reusable asset

Composition plane
  archetype/template -> compatibility planning -> data/auth/connectors/UI binding
  -> application assembly

Runtime plane
  execution/sandbox -> verification -> release/deploy -> operations

Learning plane
  telemetry/outcomes -> asset and pattern scoring -> improved retrieval and recipes
```

The Block Contract belongs between the supply and composition planes. It is not the whole platform.

## 3. Domain ownership map

### D01 — Outcome and demand modelling

**Owns:** buyer, painful job, desired outcome, constraints, value hypothesis, success measure and non-goals.

**First-principles questions:**

- What human or business state must change?
- Who experiences the pain and who pays?
- What is the smallest workflow that delivers measurable value?
- Which steps require judgment, which are deterministic, and which are merely administration?
- What existing system of record must remain authoritative?
- What must be true for the client to call the build successful?

**Existing inputs:** AutoSaaS opportunity intake/research/spec constitution; Actionist's 17 industries, 12 teams, 66 use cases and 72 ideas; industry signal and contradiction reports.

**Output:** `OutcomeSpec`, independent of implementation.

### D02 — Industry and domain ontology

**Owns:** domain entities, events, roles, terminology, obligations, invariants and common workflow atoms.

**First-principles questions:**

- Which concepts are universal and which are industry-specific?
- What is a true domain invariant rather than a feature copied from competitors?
- Which entity owns each state transition?
- Which industry differences are labels, policies, workflow differences or genuinely different data models?
- Can several industries share one archetype with a small domain delta?

**Existing inputs:** niche→atom→block joins; 12 atoms; 10 B2B archetypes; industry-specification and contradiction ledgers.

**Output:** versioned domain packs, not application code.

### D03 — Product specification and acceptance model

**Owns:** workflows, screens, actions, roles, data needs, integrations, failure states and acceptance tests for one build.

**First-principles questions:**

- What observable workflow proves the product outcome?
- What can be removed from v1 without destroying that outcome?
- Which requirements are functional, experiential, operational or compliance-related?
- Which claims can be converted into deterministic tests?
- Which unknowns must be learned through a prototype rather than prose?

**Existing inputs:** AutoSaaS run packets and gates; synthetic operations pilot; composition fixture suite.

**Output:** `ProductSpec` plus executable acceptance fixtures.

### D04 — Source intelligence and retrieval

**Owns:** local/GitHub/product discovery, indexing, dedupe, classification and retrieval against a product need.

**First-principles questions:**

- Are we looking for a whole product, engine, feature, component, schema pattern, workflow or visual precedent?
- What evidence predicts adaptation value better than stars?
- How should search combine semantics, architecture, runtime, feature and industry signals?
- When have we searched enough?
- How do we avoid finding the same fork or product surface repeatedly?

**Existing inputs:** 500 prioritized GitHub candidates; 17,000 industry×dimension observations; 118 competitor surfaces; Great Library; local corpus inventory; 8,515 joined 21st identities; unresolved Mini corpus.

**Output:** ranked `SourceCandidate` records. Discovery is not qualification.

### D05 — Capability mining and system understanding

**Owns:** explaining what a source actually provides and locating its architectural seams.

**First-principles questions:**

- What outcome-bearing capabilities exist inside the source?
- Where are data, UI, workflow, policy and integration boundaries?
- What assumptions are implicit in its framework, process model and runtime?
- Which parts are generic engines and which define a product's distinctive behavior?
- What is the smallest useful capability boundary?
- Is reuse cheaper than reimplementation after dependencies and adaptation are counted?

**Existing inputs:** AutoSaaS repo review/system extraction; Phase-7 dimension evidence; SISOCRM donor analyses; platform deep dives.

**Output:** `CapabilityMap` and candidate cut lines.

### D06 — Reuse-shape and ownership decision

**Owns:** deciding how a capability should enter the platform.

**Allowed shapes:** intact service, intact embedded module, transplanted subsystem, extracted package, generated-from-pattern implementation, data/API adapter, visual precedent, or custom build.

**First-principles questions:**

- Would upstream plausibly improve something we want?
- Is the capability more expensive to own or more expensive not to own?
- Does it define product feel or provide a generic engine?
- Can it be isolated behind a stable protocol?
- What upgrade burden does each shape create?
- What is the cheapest reversible experiment that tests the seam?

**Existing inputs:** SISOCRM ownership model; Twenty/Teable/AFFiNE/Plane/Documenso practice; Phase-8 packaging modes.

**Output:** `ReuseDecision`. This decision precedes extraction and prevents “convert everything into the same package” thinking.

### D07 — Extraction, adaptation and packaging

**Owns:** producing a bounded deliverable from the chosen source shape.

**First-principles questions:**

- What is the minimum dependency closure?
- Which source assumptions must be preserved and which must be adapted?
- Can adaptation be expressed as a repeatable transform?
- Which changes are syntactic and which require semantic judgment?
- What host-specific glue should stay outside the reusable asset?
- How is the asset upgraded, rolled back or replaced?

**Existing inputs:** Phase-8 repo-to-block mechanics; SISOCRM absorption/transplant patterns; AutoSaaS extraction notes; AST/codemod standards research.

**Output:** packaged asset plus adaptation recipe. Qualification is a separate domain.

### D08 — Thin capability contract

**Owns:** the minimum stable description needed to use a reusable capability.

**Core fields:** identity/version; capability kind; packaging mode; provided and required ports; configuration; state/data expectations; lifecycle hooks; compatibility constraints; owner; replacement/rollback hook.

**First-principles questions:**

- What must a composer know without reading implementation source?
- Which guarantees are semantic and which are deployment-specific?
- What can be checked mechanically before composition?
- How do capabilities declare optional versus required dependencies?
- How are actions, events, data resources and UI surfaces named without collisions?

**Existing inputs:** Block Contract v0/v1; Universal Block Framework; Great Library schemas.

**Correction:** rights, economics, screenshots, benchmarks and admission decisions belong in a linked qualification dossier. They should not inflate the semantic capability interface.

**Output:** `CapabilityContract`.

### D09 — Registry, graph and version resolution

**Owns:** canonical asset records, versions, dependency graph, compatibility, replacements, deprecations and retrieval indexes.

**First-principles questions:**

- What is the canonical identity across forks, moves and packaging variants?
- How do applications pin exact versions while still receiving repair paths?
- How are dependency and incompatibility edges represented?
- Can one source yield many assets and one asset have many packaging variants?
- How does the registry distinguish “known,” “qualified,” “production-proven” and “recommended for this host”?

**Existing inputs:** Great Library lifecycle and work/release/source records; Phase-7 identity edges; AutoSaaS template registry.

**Output:** asset graph and resolver API.

### D10 — Data plane and state ownership

**Owns:** product records, persistence classes, schema ownership, data capabilities, events, search/indexes, files and migrations.

**First-principles questions:**

- What state exists, who owns it, and what is its source of truth?
- Is state transactional, collaborative, evented, analytical, ephemeral, document/blob or search-oriented?
- Does a reused service retain its native store, or does an owned capability use platform storage?
- What is the stable data port above the storage implementation?
- Who owns each table and migration? Never two owners.
- How are cross-system views produced: direct query, API, events or replicated read model?
- What consistency, latency, query and recovery properties are actually required?

**Database decision:** do not standardize every asset to Postgres. Standardize the **data capability interface**.

Recommended defaults:

| State class | Default | Reason |
|---|---|---|
| Platform/control metadata | Postgres | relational, transactional, operationally familiar |
| New owned B2B application data | Postgres behind typed ports | broad feature fit and ecosystem; replaceable below the port |
| Intact donor/service data | donor-native store, isolated ownership | avoids permanent forks and migration collisions |
| Cross-service product views | SISO-owned event/read model | avoids brittle cross-schema coupling |
| Local/ephemeral tool state | SQLite/libSQL where appropriate | smaller operational surface |
| Files/blobs | object/file storage capability | databases are not the universal blob contract |
| Search/analytics/realtime | specialized capability only when required | choose from workload, not fashion |

Postgres is therefore a production default, not a universal block invariant. ORM choice is adapter-local and must not enter the capability contract.

**Existing inputs:** SISOCRM data-layer decision; Teable/Twenty convergence; reusable-block Postgres adapter guidance; existing Supabase/Convex/Postgres projects.

**Output:** `DataResourceContract`, schema-owner map and adapters.

### D11 — Identity, tenancy, authority and secrets

**Owns:** user/workspace identity, permissions, delegated authority, tenant boundaries, consent, credentials and audit.

**First-principles questions:**

- Who is acting, for which tenant, under whose authority?
- What actions can be performed automatically, staged for approval or never performed?
- Is tenancy enforced at UI, API, service and storage boundaries?
- Which component owns sessions, and how do donors accept host identity?
- How are connector credentials scoped and revoked?
- What proof shows one tenant cannot observe or mutate another?

**Existing inputs:** Block Contract authority/tenant fields; two-tenant NO_SHIP fixture; SISOCRM host-session injection; OpenConnector tenancy failure.

**Output:** host identity/authority contract consumed by every action-capable subsystem.

### D12 — Connector and external-action plane

**Owns:** provider catalogue, auth setup, normalized actions/triggers, connection tenancy, retries, rate limits and external receipts.

**First-principles questions:**

- What should be normalized across providers and what must remain provider-specific?
- Is the reusable unit a provider definition, action, trigger, workflow or connection runtime?
- Who owns OAuth configuration and each tenant's credentials?
- How are idempotency, retries, approval and side-effect receipts represented?
- When should browser operation replace API integration?

**Existing inputs:** OpenConnector 1,445 providers/15,156 actions; Activepieces 761 pieces and UI patterns; Nango 982 providers; Jentic ~4,140 OpenAPI specs.

**Output:** `ConnectorContract` and tenant-scoped connection service. Provider catalogue and connection storage must remain separable.

### D13 — UI system, interaction primitives and taste

**Owns:** design tokens, components, interaction states, accessibility, responsiveness, visual retrieval, preview and preference learning.

**First-principles questions:**

- Which UI primitives are truly reusable versus page-specific compositions?
- What semantic tokens allow a component to change brands without losing hierarchy?
- How are loading, empty, error, dense-data and destructive states represented?
- How do users express taste more reliably than prose?
- How do we measure visual coherence across independently sourced capabilities?
- When is a screenshot a useful precedent but not reusable code?

**Existing inputs:** `siso-ui-base` forge→gate→judge pipeline; 7,949 new and 3,506 source-bearing legacy 21st entries; 8,515 union; UI Opus findings; Actionist taste demo; AutoSaaS component requirements.

**Output:** design-token contract, component registry, visual precedent index and preference profile.

### D14 — Archetypes, templates and product shell

**Owns:** reusable app-level compositions: navigation, core entities, workflows, pages and default capability bundles.

**First-principles questions:**

- What repeats at the application level beyond individual components?
- Which archetypes explain most target demand?
- What belongs in the universal shell versus an archetype versus an industry delta?
- Does a fixed five-area shell improve usability or force every product into an inherited metaphor?
- Which template variation points are safe for agents to fill?

**Existing inputs:** B2B shelf with 10 archetypes; 17-industry mapping; AutoSaaS base template and five-area ISSO shell; Twenty/NocoBase/Cal.com/Directus metadata patterns.

**Correction:** the fixed five-area shell is a hypothesis to evaluate, not a constitutional rule. Case/workflow and portal are higher-demand but thinner than generic dashboard/CRM starters.

**Output:** `ArchetypeTemplate` as a versioned composition recipe, not a copied monolith.

### D15 — Composition planner and compatibility solver

**Owns:** converting a ProductSpec into a feasible assembly plan.

**First-principles questions:**

- Which choices are deterministic constraint solving and which need model judgment?
- Can incompatible candidates be eliminated before spending model tokens?
- How are namespace, port, data-owner, authority, UI and runtime conflicts detected?
- How are complete services composed with extracted packages and generated glue?
- What makes a plan underdetermined, and how is missing information requested?
- What objective is optimized: build time, quality, maintainability, latency, cost or novelty?

**Existing inputs:** Phase-8 plan-then-fill architecture; deterministic solver; 26 fixtures/10 solver checks; AutoSaaS build waves.

**Output:** `AssemblyPlan` with selected assets, bindings, glue budget and verification plan.

### D16 — Runtime, isolation and host platform

**Owns:** where code/services run, resource boundaries, networking, jobs, event delivery, previews and host APIs.

**First-principles questions:**

- Is the unit in-process code, iframe/microfrontend, sidecar, service, worker or scheduled job?
- Which failures can contaminate other tenants or capabilities?
- What host capabilities are available for data, auth, files, secrets, events and logs?
- Which resources and network destinations are allowed?
- How are previews isolated from production?
- How can a capability be killed, restarted or replaced independently?

**Existing inputs:** Lovable/platform deep dives; sandboxd/Modal/Astryx research; SISOCRM service mounting; Block Contract runtime fields.

**Output:** `HostContract` and runtime profiles. There may be several valid profiles; “one runtime for everything” is not required.

### D17 — Verification, qualification and promotion

**Owns:** evidence that an asset and assembled application meet their declared guarantees.

**First-principles questions:**

- What claim is being tested, and what would falsify it?
- Which tests apply to an individual capability, a binding, an archetype and the whole application?
- What must be tested in a clean environment?
- Which visual and workflow judgments require humans?
- How do we separate “builds,” “works on fixture,” “works in host,” and “works for client”?
- What evidence should change retrieval ranking after production use?

**Existing inputs:** 14 receipt types; nine evidence families; siso-ui-base gates/judge; 7-gate/20-task pilot; 26 composition fixtures; AutoSaaS verifier.

**Output:** linked `QualificationDossier` and promotion decision. Legal/rights can be a downstream dossier handled by the appropriate people; it is not the core quality architecture.

### D18 — Release, operations, economics and learning

**Owns:** Git/version history, deployment, migrations, rollback, health, usage/cost, support, upgrades and feedback into the factory.

**First-principles questions:**

- What exactly is released and pinned?
- Can every data/code/config change be rolled back or compensated?
- How is a failing capability isolated and replaced?
- What does one accepted build and one maintained client cost?
- Which reusable assets reduce future delivery time in practice?
- What production outcomes should promote or demote an asset/template?
- How are client-specific deltas kept from fragmenting the platform?

**Existing inputs:** Great Library releases/lifecycle; AutoSaaS launch-and-learning loop; Cloudflare/subdomain deployment work; SISOCRM backup/restore and service scripts.

**Output:** `ReleaseManifest`, operational receipts and learning events.

## 4. The contracts between domains

The platform needs several small contracts, not one enormous universal manifest:

| Contract | Producer → consumer | Purpose |
|---|---|---|
| `OutcomeSpec` | D01 → D02/D03 | Defines value and constraints |
| `ProductSpec` | D03 → D04/D14/D15 | Defines the requested product and acceptance |
| `SourceCandidate` | D04 → D05 | Discovery record |
| `CapabilityMap` | D05 → D06 | Explains source capabilities and seams |
| `ReuseDecision` | D06 → D07/D16 | Selects service/module/package/pattern/custom shape |
| `CapabilityContract` | D07/D08 → D09/D15 | Thin semantic interface for reuse |
| `DataResourceContract` | D10 → D15/D16 | Storage-independent data capabilities |
| `HostContract` | D11/D16 → D08/D15 | Identity, authority and runtime capabilities |
| `ConnectorContract` | D12 → D15 | External actions and events |
| `ArchetypeTemplate` | D14 → D15 | App-level composition recipe |
| `AssemblyPlan` | D15 → D07/D16/D17 | Exact bindings and glue work |
| `QualificationDossier` | D17 → D09/D18 | Evidence without bloating semantic contracts |
| `ReleaseManifest` | D18 → operations/learning | Deployed version and recovery path |

## 5. Where the existing framework was forcing the answer

### Assumption A — every useful repository becomes one standardized block

Rejected. Repositories are source containers. Useful outcomes may be intact services, embedded modules, extracted packages, adapters, patterns, datasets or complete templates. Standardize the seams and records, not all implementations.

### Assumption B — all blocks standardize onto Postgres

Rejected as a universal invariant. Keep Postgres as the default for new owned transactional state. Expose typed data capabilities above it. Mature donors retain native data ownership unless a measured reason justifies transplantation.

### Assumption C — the Block Contract should contain everything

Rejected. Split the semantic capability contract from packaging, host binding, qualification evidence, registry status and release state. A composer needs a small stable interface; auditors and operators need richer linked dossiers.

### Assumption D — a five-area dashboard shell fits every SaaS

Unproven. It is one archetype hypothesis. It should compete against case/workflow, client portal, CRM, finance operations, scheduling, support and field-operation shells using workflow success and user comprehension.

### Assumption E — “repo-to-block automation” is the main moat

Incomplete. The durable moat is the whole learning system: demand ontology + capability graph + reuse-shape decisions + qualified assets + templates + compatibility solver + production feedback. Conversion alone can create a large shelf nobody needs.

### Assumption F — one agent should build the application

Rejected. Deterministic services should own retrieval filters, dependency resolution, namespace checks, data ownership and verification. Models should interpret demand, choose among feasible alternatives, write bounded adaptation/glue and explain trade-offs.

## 7. Recommended order of reasoning and experiments

Do not begin by selecting 1,000 repositories. First establish the interfaces that make repository quality comparable.

1. **Freeze this domain map only provisionally.** Challenge missing domains and bad boundaries.
2. **Thin the Block Contract.** Separate semantic capability, packaging, host binding, qualification and release records.
3. **Define the Host Contract.** Data, identity, secrets, files, events, UI mount and runtime profiles.
4. **Run a data-plane bake-off from workloads, not brands.** Use 8-12 representative capabilities and compare direct Postgres, typed Postgres adapter, donor-native service, SQLite/local and API/event read-model shapes.
5. **Choose three deliberately different reuse pilots:** an intact service, an extracted UI/domain package and a generated-from-pattern capability.
6. **Compose one narrow case/workflow or client-portal application.** These are demand-rich and supply-thin, so they test the real thesis better than another generic dashboard.
7. **Measure adaptation hours, glue size, defects, runtime burden, visual coherence and client-outcome fit.** Those measurements determine the top 1,000; stars and metadata alone do not.

## 8. The strategic answer

Actionist should not be “Lovable with more repositories.” It should be a **semi-custom software assembly operating system** whose advantage is knowing:

- what clients repeatedly need;
- what reusable capabilities actually exist;
- which reuse shape is correct for each source;
- how heterogeneous capabilities can safely share data, identity, UI and runtime;
- which compositions have already worked;
- and how to deliver the next industry product with less bespoke work.

The core abstraction is therefore not merely a block. It is a graph:

```text
outcome
  -> domain atoms
  -> product specification
  -> reusable capability contracts
  -> packaging/runtime variants
  -> data/auth/connector/UI bindings
  -> archetype composition
  -> qualification evidence
  -> released application
  -> production learning
```

That graph lets each domain own one kind of truth while still allowing the whole system to compose.
